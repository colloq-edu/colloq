In a k3s installation the app runs as UID 1000 with no Docker socket and no Kubernetes credentials. Only the private runtime broker gets a namespaced service-account token, and it creates Pods and Services from a fixed template and a trusted catalog. The API doesn't accept an arbitrary Pod template or host path. The ready-made image recommended for universities works differently: the app holds the Docker socket, which is root on the VM; see Your own server (university).

Each room gets its own Jupyter Pod, token and workspace subPath. If the runtime, the image or a policy is unavailable, nothing starts: there is no fallback to a shared server kernel.

Pod restrictions

A room Pod runs as UID/GID 1000 with no extra capabilities and no privilege escalation, with the RuntimeDefault seccomp profile and a read-only root filesystem. The service-account token is not mounted. Writable areas: the room directory, /tmp, /home/runner and /dev/shm.

Pod Security enforces the restricted profile. The broker's RBAC is limited to Pod and Service operations in the namespace; the only way it can change a running Pod is the pods/resize subresource, which it uses to change a room's memory. But RBAC can't restrict every field of the Pod being created, so the broker's code, its templates and the catalog are part of the trusted base.

Network: check the actual result

NetworkPolicy allows inbound connections to Jupyter only from the app and the broker. By default, rooms may send traffic out only to the DNS Pod in kube-system over TCP/UDP 53. To download external data you need a separately designed outbound proxy or profile.

The local node exception

A standard NetworkPolicy doesn't prove that student code can't reach services on the node where its Pod runs. An enabled host firewall protects what is exposed publicly, but it doesn't close this gap by itself.

If you need isolation from host services, add a CNI with host policy or a tested firewall policy that allows only the broker to reach the Kubernetes API. Before you let untrusted users in, run a real room-to-node connection test. Having a manifest is not proof.

Files and quotas

Linux production accesses files through trusted file descriptors, O_NOFOLLOW and /proc/self/fd. Symbolic links can't escape the room directory. If the protected mechanism is unavailable, production refuses to run.

An old workspace must not contain hard links between rooms. When migrating, copy regular files into separate directories and check owners and links. Path checks don't turn two names of an existing shared inode into independent data.

PVC size is scheduling metadata, not a filesystem quota. MAX_UPLOAD_MB and MAX_SESSION_MB limit what the app does and don't stop Python from writing whatever it wants. Use a separate partition and monitor free space.

Competitions: what is closed and what is not

A competition submission runs in a throwaway container: one per submission, no network, data read-only, under the same hardening a room gets (uid 1000, no capabilities, no-new-privileges, a process ceiling, a read-only root, memory and CPU caps). The container is destroyed once the submission is done.

The hidden answers (solution.csv) and your metric code live in the competition's directory under DATA_DIR and never in a class workspace. They do not enter the container that runs an entrant's notebook at all: the metric is computed by a second container, which by then holds neither the entrant's data nor their code. The split seed leaves through no /api/k door.

A competition does not replace an exam

It scores a notebook; it does not attest to who wrote it. Two entrants submitting one solution under two names, one person holding two entry keys, or a key handed to a neighbour are all outside what the server can see. Fitting the public leaderboard by submitting repeatedly is a strategy, not an attack: the private share and the daily quota make it expensive, not impossible. If a grade rides on the result, invigilation stays with you.

Submission machines

A submission machine runs the notebooks of this server's competition submissions on its own Docker, in the same throwaway sandbox with no network as the server. It gets the notebooks of the submissions it runs, the competition's open data and the ready package sets of its participants. Only a trusted machine gets the hidden test, and trust is off by default. The hidden answers, the metric code, scores, names, emails, sign-in keys and the database never go to a machine: the server still runs the metric. Remember that a participant's notebook may hold anything they wrote in it.

The code and the secret. When joining, a machine presents the owner's code: 128 bits, for the number of machines set and a day at most; the server keeps only its fingerprint, and only the owner mints codes. The owner can cancel a code still valid before it expires (Cancel under Join codes), and Disconnect all cancels every code still valid too: otherwise whoever still holds a code could join a new machine with it. In return the machine gets a secret of its own, 256 bits; the server keeps its sha256 and compares it in constant time. The secret travels only in the Authorization header and only to /api/runners/v1: no other door of the server — the panel, the competition page, rooms, WebSockets — accepts it, and the machines' door accepts no staff cookie, participant key or room token. The relay token never reaches a machine: it opens no address and calls the server by itself.

Disconnecting. Disconnect in the panel takes effect at the machine's next call: the server answers 401, its runs go back to the queue at no cost to participants, late results are refused, and the agent purges the hidden test and stops. Taking trust away likewise sends its runs with the hidden test back to the queue, cuts a download of the test short, and purges the test from the machine. Minting a code, in the panel or with colloq-host runner-code, cancelling codes, connecting a machine, trusting it or taking trust away, and disconnecting it go into the Audit log. In the log, a code minted with the command, and a machine that joins with it, show Server console where a person would stand; Join codes shows such a code as minted on the server's console.

What comes back the server takes as participant data: only two files with known names, size limits after decompression, a sha256 check, staging outside the attempt directories, and a check that the result belongs to that very attempt. The texts a participant reads, the brief ones under a hidden test included, the server writes itself.

What this does not close

A machine whose secret was stolen, or which was broken into, sees the notebooks of its submissions — rivals' code in the middle of a competition — and the hidden test if it is trusted, and can send forged results for the submissions it holds. It gets no hidden answers, no metric, nobody else's submissions, no rooms and no other machines; its places, the run ceiling, disconnecting, quarantine and the event log limit it. Whoever runs the host of a rented VM sees everything on it, a trusted machine's hidden test included. Machines do not sign their requests: TLS ends at the reverse proxy or relay in front of the server, and whoever controls it can read the machines' secrets and pose as the server — as they can read staff cookies today. The agent holds the Docker socket, which is root on its machine: a submission machine, like the server, must be dedicated.

Access, links and secrets

A room link gives access to the class; a teacher's sign-in link gives access to the panel. The setup token lets an owner regain control. Keep secrets and backups private; full access to the server's disk means access to its data and keys.

Separate answers in a Council don't give each student their own kernel. The “Dangerous commands” rule refuses the lines that end a kernel out of curiosity (exit(), os._exit(), %reset, !kill -9 -1, rm -rf of the class folder), but it is a speed bump, not a sandbox: ctypes, a fork bomb and the room's terminal all walk past it. Action limits and browser bans don't verify identity. The system doesn't promise automatic grading, SSO or protected exam execution.

Deployment limits

Containers share the VM's Linux kernel. This is not VM-level isolation and doesn't protect against kernel vulnerabilities. One VM, one k3s node and local PVs give no HA. If the machine is lost, you need an external backup; updates interrupt work and lose Python memory.

A starting point for resources, scenarios and a formula for memory are under Machine and sizing. Those numbers are derived from the limits in the code, not from a load test, so check them against your own classes: the load depends on the computation, output, files, active rooms and network.

A class on your own computer

A local run — colloq start or make dev — listens on 127.0.0.1 only; the class is visible from outside only after an explicit colloq host. Room kernels are separate Docker containers, and the server manages them through the Docker daemon, which amounts to root on that machine. On macOS every path segment is opened with O_NOFOLLOW, but without the Linux /proc/self/fd mechanism a race window remains between the check and the operation.

Every room container gets the same hardened profile, however the class was started (colloq start, make dev, make run, make up, the vast.ai image): UID 1000, no Linux capabilities, no-new-privileges, Docker's default seccomp profile, a process limit (KERNEL_PIDS, 512 by default) and no IPv6. Students' personal notebooks run in the class's second container — the same profile, but with its own process ceiling (KERNEL_OWN_PIDS, 2048 by default), its own Jupyter token and no access to the class's GPU. The room reaches the internet — pip install, datasets, APIs — but not local addresses: 10/8, 172.16/12, 192.168/16, 100.64/10, link-local 169.254/16 with cloud metadata, loopback, multicast, the computer itself and the other rooms. A connection there is refused at once. Under make up and in the vast.ai image rooms share a Docker network with the server, and traffic inside that network is filtered only when the host passes bridged traffic through iptables, as Docker normally arranges; otherwise the per-room Jupyter token still stands between rooms. Only DNS on port 53 stays open to any address, because on some machines Docker's resolver forwards queries from the room's own network.

The server installs this block itself: a short-lived privileged helper container adds rules to chains of its own, COLLOQ-ROOMS-*, reached from DOCKER-USER and INPUT, with the same iptables the Docker daemon uses. It is built for colima, Docker Desktop and Docker on Linux; rootless Docker, podman and Docker Desktop with Enhanced Container Isolation don't allow the helper. If the rules can't be installed, rooms don't start, and the message in the room says why. For a trusted class that needs the local network, the line COLLOQ_ROOM_NETWORK=open in .env lifts the block, and colloq doctor then points it out. A room container started by an older version keeps its old profile until it stops; the next start recreates it.

Unlike a production room, the root filesystem stays writable so that %pip install works, and nothing limits how much disk a room uses. So a local class is still meant for a trusted setting — “my class on my computer”; for an open audience, use a server install.
