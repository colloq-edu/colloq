# Competition execution on k3s

Status: implemented with a one-node k3s smoke for notebook, scorer, inventory and package preparation, 2026-09-23. User approved the staged implementation: notebook and scorer first, Dependency Manager second.

A single application and a single private runtime broker own the instance. Application and broker communicate with the existing runtime bearer token. Only the broker has Kubernetes credentials. The app and one-off workloads mount `colloq-data` on the existing single k3s node. Kubernetes image references are registry images pinned by digest from the release catalog; local Docker image IDs are not substituted for them.

## One-off notebook and metric jobs

The app sends a validated intent containing opaque job/competition/submission/attempt IDs, the selected catalog environment and digest, bounded limits, and optionally the ready bundle ID. It never sends a Pod template or an arbitrary path. Broker derives PVC `subPath` values from validated IDs. It creates a short-lived Pod with two containers, no ServiceAccount token, a read-only root, uid 1000, dropped capabilities, process/resource/ephemeral limits, bounded logs and a memory-backed shared `/out` volume. A default-deny NetworkPolicy prevents internet access. The broker may reach only a token-authenticated trusted export sidecar on a dedicated port.

The notebook container sees public data, its own notebook and optionally its own published wheel bundle read-only. It never mounts `secret/` or a writable host directory. The scorer runs in a separate Pod and sees only its attempt's metric/secret snapshot and validated CSV. It receives neither the notebook, public data nor participant packages. The app's existing harness runs in each image via a read-only mounted script directory, retaining metric validation, offline venv installation, progress and verdicts.

The exporter sidecar uses the pinned runtime image and alone mounts the bounded destination on the data PVC. The main container never sees that mount. After the main process terminates, the broker tells the sidecar to export only an allowlist of regular files (`run.json`, `progress.json`, `executed.ipynb`, `submission.csv` for notebook; `score.json` for scorer). The sidecar checks byte ceilings, names, file types and symlinks before atomic copies. A unique attempt ID and matching report nonce still gate acceptance in the app. Cancellation and timeout delete the Pod; restart reconciliation lists and deletes only Pods carrying this instance's job label. App paths, public/secret separation and per-attempt output directories remain unchanged.

## Package preparation and base inventory

For broker mode the app pins the selected registry digest and gets Python/ABI/platform and the **actual full installed package inventory** by a one-off offline probe, not by treating the release's direct requirement lines as the full inventory. This revision is stored by the existing immutable schema. If an old local Docker revision has no matching published catalog image, it remains historical and cannot be claimed as a k3s execution image.

The existing requirements parser, wheel-only restrictions, base constraints, hashes, zip limits and offline verification remain authoritative. The resolver runs as a separate Pod without competition data or secrets. A short-lived proxy Pod has no data mounts and allows CONNECT only to PyPI/package file hosts after public-IP resolution, as the current Docker proxy does. Kubernetes NetworkPolicy allows resolver egress only to its proxy and cluster DNS. Proxy egress is TCP 443 plus DNS, and the proxy itself rejects other hosts. Downloaded wheels land only in the private staging directory on the data PVC, with the existing stage/CAS verification and disk limits. The verifier uses a second Pod with no network and read-only wheels; only after its success does the app publish the bundle. Any Pod, proxy or service left by a restart is reconciled by broker-owned labels and a bounded age.

## Protocol and readiness

The runtime broker exposes authenticated, bounded `/v1/competition-jobs` routes for start/status/collect/cancel/list, and the app has a `CompetitionRunner` adapter. The private protocol parses every field, rejects arbitrary paths and unrecognized resource limits, and never returns hidden scorer tracebacks to participants. The app selects broker when `KERNEL_BACKEND=broker`, while local Docker and the fake test runner keep their existing behavior. Base inventory, preparation and notebook/scorer readiness are separate health capabilities. Missing catalog image/PVC/exporter/proxy policy produces a precise refusal before accepting work. Durable queue leases, pinned revisions, retry and UI statuses keep the same product contracts.

## Deployment and verification

The published runtime image includes the exporter entrypoint. Release manifests mount the data PVC to the broker, grant only the required Pod/read-log operations to its service account and add the one-off Pod/proxy network policies. The release catalog includes `kaggle-base` for the PVZ competition. No Docker socket is mounted into the production app.

Tests first exercise a fake Kubernetes API, inspect Pod mounts/NetworkPolicies and cross-instance cleanup, then use a disposable local k3s/k3d cluster. The real-cluster smoke covers package preparation, an offline notebook and a separate metric. Cancellation/restart and restore with pinned replay are checked by fake/unit/release tests and remain to be verified on a real cluster before broader release qualification.

## Disposable real-cluster smoke status

`node --import tsx scripts/competition-k3s-smoke.mts --dry-run` plans a unique k3d cluster, private local registry, fixture under `scratchpad/k3d/fixture-<random>/`, and a kubeconfig inside that fixture. `--preflight` reads Docker capacity without creating resources. `--run` is opt-in, builds the app/runtime/base kernel for the Docker host architecture, pushes only to its own local registry, pins registry digests in a temporary release catalog, starts k3s, and runs a broker-backed notebook and separate scorer from a fixture app Pod on the private PVC. `--include-kaggle` also builds the larger CPU Kaggle image; `--prepare` runs inventory and dependency resolution/verification. On macOS, `--colima-profile NAME` routes all Docker and k3d work to that profile's socket without changing the global Docker context. The Linux amd64 nightly/manual workflow uses the same script and does not publish to an external registry.

On 2026-09-23, the default Colima Docker filesystem had only 1.31 GiB free, so `--run` refused before creating any resources. A separate `colloq-smoke` profile with 25 GiB disk and 6 GiB RAM passed preflight. The real `--run --prepare --colima-profile colloq-smoke` run produced the local ignored report `scratchpad/k3d/fixture-76075fba4c7c/report.json`: digest-pinned ARM64 app/runtime/base images pulled from its private registry; a notebook ran offline and produced a CSV; a separate metric Pod returned public/private MAE `0`; an inventory Pod reported the installed base; resolver plus restricted CONNECT proxy downloaded two wheels; and a network-free verifier accepted them. A selected Pod had three consecutive refused external TCP connections before jobs started, and the notebook's own egress assertion also passed. Captured Pod specs show the notebook main had only public data/input, metric main had only the secret snapshot/input, resolver main had input/wheels without competition data, proxy had no data PVC, and `/result` appeared only in trusted exporters. The run deleted its cluster, registry, local tags, empty network, and temporary kubeconfig. The default Docker context and Kubernetes current context were unchanged; the script's default kubeconfig content hash guard did not fire.

This is a real one-node k3s proof for the base environment, notebook, scorer, inventory, proxy resolution and offline verification. It does not cover the larger `kaggle-base` image, cancellation, restart reconciliation, restore/pinned replay, node-local traffic bypass, or the Linux CI runner. Cancellation, restart and restore/pinned replay have fake/unit/release checks, but still need separate real-cluster results. An early run exposed a k3s NetworkPolicy propagation race: the broker failed closed before starting the notebook. The broker now waits up to 30 seconds for three consecutive denied egress probes before starting a job; the successful run used that fix and an independent policy check. During manual cleanup of that first failed fixture, a k3d command omitted the temporary `KUBECONFIG`: the default kubeconfig modification time changed, although its context names and current context appeared unchanged. No speculative restoration was attempted. Later scripted runs always set a fixture kubeconfig and confirmed its default file content hash stayed unchanged.
