# Аудит всего продукта Colloq

Дата: 22 сентября 2026. Проверенный коммит: `797218e5a1b3afc72fca75cd0932a5a188dea77e`.

## Вывод

Найдены **23 воспроизведённых дефекта**, отдельно — ограничения поставки, неоднозначное поведение настроек и гипотезы для следующего прохода. Самые существенные проблемы связаны с отзывом прав на уже открытых соединениях, сохранением изменений после потери связи и ошибок записи, жизненным циклом попыток исполнения и достоверностью лидерборда.

Большое число проходящих тестов не означает готовность релиза: **GitHub CI последнего коммита завершился ошибкой**. Linux выявил проблему длинных имён файлов, а проверка документации — отсутствие пересборки опубликованных страниц. Сборка production Docker-образов, pip-пакета и typecheck в этом же CI прошли.

Аудит не вносил исправлений в исходный код и не менял живые занятия, соревнования или настройки. Все проверки состояния проводились во временных каталогах, с отдельной SQLite и подставными сервисами. Единственная новая проверка в настоящем контейнере создала два крошечных файла в одноразовом `/tmp`, без сети. Рабочие Docker/Kubernetes нагрузки не останавливались.

## Как распределялось погружение

1. **Обзор всего продукта.** Карта подсистем, ролей, хранилищ и поддерживаемых способов поставки; изучение CI текущего коммита. Первоначально узкий проход по соревнованиям после уточнения задачи стал частью общего аудита.
2. **Подробная проверка границ.** Независимые проверки исполнения, пакетов, интерфейсов соревнований; затем runtime комнат, AI, совместного редактирования. Отдельно проверялись авторизация, файлы, публикации, CLI, бэкапы и поставка.
3. **Воспроизведение.** Углубление только в конкретные сценарии. Использованы настоящие функции и обработчики, SSR Svelte, временные БД, управляемые ошибки I/O и подставные ответы Docker/Kubernetes. Тесты воспроизведения утверждают наличие дефекта — их зелёный результат не означает его исправление.
4. **Перекрёстная проверка.** Перепроверены достижимость отзыва прав, фактические ограничения production и защитные условия вокруг offline-очереди. Сведения о поддержке k3s сверены с README: ограничение действительно задокументировано и не выдано за скрытую уязвимость.

Контекст сохранялся отдельными отчётами по подсистемам. Это позволило не перечитывать весь репозиторий для каждой гипотезы и оставить время на проверки за пределами новых соревнований.

## Подтверждённые дефекты основного продукта

### F01 · P1 · Удаление преподавателя не отзывает права уже открытого control-сокета

`server/src/index.ts:268`, `server/src/control.ts:5323`, `server/src/control.ts:5455`, `server/src/routes/admin-auth.ts:338`.

Роль вычисляется при подключении, затем замыкается в обработчике. Удаление преподавателя или ротация его ссылки не закрывают соединение и не обновляют эту роль. Воспроизведение: после удаления преподавателя новый `roleFor()` вернул `participant`, но старый сокет успешно выполнил преподавательское `class:finish`. Heartbeat проверяет жизнеспособность соединения, а не актуальные права. Независимая повторная проверка не нашла серверного пути отзыва.

**Исправление:** хранить источник полномочий и версию авторизации у соединения; отзывать связанные соединения при изменении сотрудника либо перепроверять полномочия перед привилегированным действием. Применить общий механизм к control, CRDT и файловым каналам. Нельзя полагаться на добровольный reconnect браузера.

### F02 · P1 · Offline-undo может сохранить промежуточный текст вместо последнего

`web/src/lib/controls.ts:68`, `web/src/lib/session.svelte.ts:775`, `web/src/lib/council.svelte.ts:429`, `web/src/components/lecture/NotesPad.svelte:326`.

Во время разрыва связи пользователь меняет черновик или заметку A → B → A. Очередь удаляет последнее A как дубликат первого, оставляя `[A, B]`; после подключения сервер сохраняет B. Сценарий воспроизведён настоящей `enqueueControl` для обоих типов снимков. Оба редактора допускают offline-правки; блокировка кнопки отправки этого не предотвращает.

**Исправление:** отдельно обрабатывать команды и снимки состояния. Для снимков сохранять последнее значение по ключу ресурса (ячейка; файл+страница), учитывая порядок относительно submit/run.

### F03 · P2 · Неудачная правка AI остаётся в документе и позже сохраняется без undo

`server/src/ai/agent.ts:1074`, `server/src/ai/agent.ts:1104`, `server/src/collab/files.ts:263`, `server/src/collab/files.ts:333`.

Открытый файл сначала меняется в Yjs, потом сохраняется на диск. При ошибке записи AI сообщает отказ и не создаёт undo-запись, но текст в общем документе уже изменён. Воспроизведение с небольшой ошибкой EIO: диск содержит `before`, документ — `after`, undo отсутствует; следующая обычная запись сохраняет `after`.

**Исправление:** согласовать публикацию изменения и его долговечность. При отказе явно откатывать изменение либо сохранять состояние восстановления и возможность отмены; отдельно проверить ошибку при самой отмене.

### F04 · P2 · Откат неосуществимого resize молча теряется при Kubernetes 409

`runtime/src/controller.ts:590`.

После принятого увеличения памяти kubelet сообщает `Infeasible`. Обновление статуса между чтением Pod и PATCH отката меняет `resourceVersion`; ошибка 409 подавляется. Воспроизведение: desired spec остаётся 8192 MiB, работающий контейнер — 2 GiB, наружу уходит обычное сообщение о невозможности resize без признака неудачного отката.

**Исправление:** повторять откат по свежему `resourceVersion` с тем же UID и ограниченным числом попыток, как прямой resize; сохранять явное состояние незавершённого согласования.

### F05 · P2 · Свободная память считается по обрезанному списку для интерфейса

`server/src/kernel/resources.ts:339`, `server/src/kernel/resources.ts:367`, `server/src/kernel/resources.ts:438`.

Сначала берутся последние 200 записей занятий, затем не более 50 подходящих строк, и уже по этому списку суммируется занятая память. Проверка с 51 живой комнатой учла только 50. После добавления 201 новой неактивной записи старые живые комнаты вообще пропали из расчёта. Kubernetes всё ещё применяет собственный admission; дефект в показаниях и планировании продукта.

**Исправление:** считать агрегаты по полному runtime census; названия и пагинацию добавлять после расчёта. Отдельно учесть второй контейнер личных тетрадей в Docker-режиме.

### F06 · P2 · Первый временный отказ Docker кэшируется до перезапуска приложения

`server/src/kernel/pool.ts:357`, `server/src/kernel/pool.ts:383`.

Если первый probe выполнен до готовности Docker/Colima, его `false` сохраняется в Promise навсегда. В тесте daemon уже восстановился, но второй вызов не сделал новый probe и снова вернул недоступность. Похожий кэш используется для сети. Это относится к локальному Docker-пути, не к broker.

**Исправление:** TTL/backoff для отрицательного результата и явный retry; объединять одновременные проверки, но не хранить временный отказ бессрочно.

### F07 · P2 · Длинные имена Unicode ломают копирование и запись на Linux

`server/src/workspace.ts:793`, `server/src/workspace.ts:956`, `shared/paths.ts:33`, `server/src/workspace.ts:538`.

Ограничение имени задано в символах, а временное имя включает полное исходное имя и UUID. Оно превышает Linux NAME_MAX в байтах. В небольшом Linux-контейнере обычное имя в 233 UTF-8 байта создалось, временное в 278 байт получило `ENAMETOOLONG`. Тот же сценарий уже падает в CI на `tests/tree-copy-server.test.mts:146`. Продукт переводит ошибку в «сейчас занят», советуя бесполезно повторить действие.

**Исправление:** короткое случайное временное имя, не зависящее от имени файла; байтовые ограничения для целевого имени и отдельная понятная обработка `ENAMETOOLONG`.

### F08 · P2 · Изменения документации не попали в опубликованный HTML

`docs/pages/ru/backup-restore.html`, `docs/pages/en/backup-restore.html`, `.github/workflows/docs-check.yml:58`.

Последний коммит изменил исходники инструкций backup/restore, но не четыре производных файла `site/docs/...`. Временная пересборка и GitHub Actions подтверждают расхождение. Проверка падает, а сайт продолжает содержать старые инструкции. Это пропуск в предыдущем завершении работы, а не случайная ошибка CI.

**Исправление:** пересобрать и включить HTML и индексы в коммит; добавить эту проверку в локальную команду подготовки изменения документации.

## Подтверждённые дефекты соревнований и зависимостей

### F09 · P1 · Вложенные файлы результата не учитываются в лимите диска

`server/src/competitions/docker-runner.ts:242`, `server/src/competitions/docker-runner.ts:435`, `server/src/competitions/docker-runner.ts:448`.

`/result` — записываемый каталог хоста. Проверка размера складывает только непосредственных потомков, считая размер самой директории вместо её содержимого. Небольшое воспроизведение с вложенным файлом показало превышение уменьшенного тестового лимита без остановки. Per-file limit не заменяет суммарную квоту. Последствие — возможное заполнение общего диска и отказ других занятий/БД.

**Исправление:** реальная дисковая квота или ограниченный канал экспорта результата. Рекурсивный учёт с пределом числа файлов полезен дополнительно, но сам по себе не даёт жёсткой гарантии.

### F10 · P1 · Пересчёт перезаписывает активную задачу и запускает её одновременно второй раз

`server/src/competitions/runner.ts:884`, `server/src/competitions/store.ts:1539`, `server/src/competitions/runner.ts:273`.

Rescore кладёт уже считающуюся посылку в очередь через upsert, превращая running в waiting и стирая владельца/container. При `slots=1` воспроизведены два одновременных scorer. Завершение первого удаляет строку очереди второго; оба используют одинаковые каталоги, поэтому очистка одного может повредить другому.

**Исправление:** отдельный неизменяемый ID попытки и проверка владельца при завершении; не заменять активную задачу. Запрос нового пересчёта хранить как следующую операцию/ревизию.

### F11 · P1 · Повтор может принять старый успешный CSV после неудачного нового запуска

`server/src/competitions/runner.ts:441`, `server/src/competitions/docker-runner.ts:584`.

Result-каталог переиспользуется, а принадлежность `run.json` и CSV текущей попытке не проверяется. Воспроизведение оставило старый успешный отчёт и ответ, затем имитировало новый контейнер с exit=1 без новых файлов: runner вернул `ok` со старым CSV.

**Исправление:** каталог и nonce на попытку, согласование exit/report, публикация артефакта только после успешного текущего запуска. Отдельно хранить подтверждённый ответ для пересчёта метрики.

### F12 · P2 · Очередь проверяет память на одну посылку, затем заполняет все слоты

`server/src/competitions/runner.ts:260`.

После одной проверки свободной памяти цикл запускает столько задач, сколько позволяет число слотов. Воспроизведение: доступно 4352 MiB, три посылки по 4096 MiB, три слота — запускаются все три. Контейнерные memory limits не являются резервированием общей памяти хоста.

**Исправление:** резервировать ресурс при каждом claim и учитывать стартующие/идущие задачи; согласовать бюджет с обычными ядрами.

### F13 · P2 · Жёсткий лимит вывода не видит продолжающуюся печать одной ячейки

`server/src/competitions/harness.ts:174`, `server/src/competitions/docker-runner.ts:431`.

После первого превышения мягкого предела обвязка продолжает считать отброшенный вывод, но не обновляет heartbeat. В проверке настоящего Python-класса внутренний счётчик достиг 70 MB, а внешнему watchdog осталось видно 3 MB. Процесс может занимать слот до wall timeout вместо предусмотренной ранней остановки.

**Исправление:** ограниченные по частоте обновления счётчика и немедленная реакция на жёсткий порог, даже когда сам текст уже отбрасывается.

### F14 · P1 · Админский лидерборд считает места по неполному feed

`web/src/admin/screens/competitions/Live.svelte:164`, `web/src/admin/screens/competitions/Live.svelte:195`, `web/src/admin/competitions.ts:527`.

При прямом открытии таблицы effect выполняется до загрузки первых 200 посылок и не повторяется по их приходу из-за `untrack`. Обновление счётчиков также заменяет полный feed первой страницей. В воспроизведении правильный результат 999 сменился на 1; есть и жёсткий потолок 2000 записей без предупреждения о неполноте.

**Исправление:** получать авторитетный leaderboard с сервера. Пагинацию ленты посылок не использовать как вход для расчёта результатов.

### F15 · P1 · Поздний ответ предыдущего маршрута смешивает два соревнования

`web/src/screens/CompetitionsScreen.svelte:176`, `web/src/screens/CompetitionsScreen.svelte:196`, `web/src/screens/CompetitionsScreen.svelte:349`.

При быстром переходе alpha → список → beta старый ответ alpha может перезаписать данные beta. Нагрузчики page/board/mine независимо присваивают результат после await без проверки поколения. Реальная функция загрузки воспроизвела позднюю запись alpha. Цели действий читаются из текущего route, а часть видимых данных — из старого page: появляется риск отправки решения не той задачи.

**Исправление:** связывать запросы и результаты с поколением `{competition, identity}`; отменять или игнорировать старые ответы и ключевать действия тем же состоянием.

### F16 · P2 · Админская лента не обновляется при части терминальных исходов

`web/src/admin/screens/competitions/Live.svelte:158`.

Fingerprint обновления не включает timeout, outOfMemory, cancelled и изменение выбора. Настоящие извлечённые effects получили эти обновления, но не сделали ни одного нового запроса feed. Summary уже новый, строки могут оставаться running.

**Исправление:** серверный revision/event для любого изменения посылки, либо события с актуальной строкой. Дополнение одних счётчиков всё равно не решит пересчёт с тем же количеством результатов.

### F17 · P2 · «В зачёт» отображается для выбора, который правило соревнования игнорирует

`web/src/components/competitions/SubmissionRow.svelte:144`, `server/src/routes/competitions.ts:747`, `shared/competitions.ts:824`.

Для `bestPublic` и `last` UI и API позволяют выбрать произвольную scored-посылку и помечают её «в зачёт», хотя общий scorer считает другую. SSR и настоящий `countedSubmission` подтвердили расхождение на одной фикстуре.

**Исправление:** вычислять пометку из активного правила; ручной выбор доступен только для `chosen`, включая API-проверку.

### F18 · P2 · На телефоне нельзя увидеть участников ниже шестого места

`web/src/components/competitions/BoardView.svelte:31`, `web/src/components/competitions/BoardView.svelte:203`.

Обе раскладки берут первые шесть строк, но кнопка продолжения есть только у desktop. SSR с девятью участниками на телефоне отрисовал шесть имён и ни одной кнопки продолжения.

**Исправление:** общая пагинация после обеих раскладок либо полный мобильный список.

### F19 · P2 · Замена бейслайна превращает старого служебного участника в обычного

`server/src/routes/admin-competitions.ts:186`, `server/src/routes/admin-competitions.ts:934`.

Очистка `baselineSubmissionId` удаляет единственную связь со служебной личностью, но её scored-результаты остаются. API-воспроизведение показало `baseline=false` у прежней служебной строки. После новой проверки могут появиться два бейслайна, один из которых участвует в обычном ранжировании и счётчиках.

**Исправление:** хранить служебную идентичность отдельно от последней проверенной посылки; не определять её только через текущий baselineSubmissionId.

### F20 · P1 · Проверенность бейслайна переживает смену метрики

`server/src/routes/admin-competitions.ts:210`, `server/src/routes/admin-competitions.ts:749`, `server/src/routes/admin-competitions.ts:1003`.

После успешного бейслайна код метрики был заменён заведомо падающим, однако `ready` осталось null, а `/open` вернул 200. Проверка не связана с ревизией входов. Аналогичное отсутствие привязки видно для environment/data/solution/split, но все эти варианты отдельно не воспроизводились.

**Исправление:** fingerprint проверяемой конфигурации и артефактов; инвалидировать readiness при его изменении. Хранить ревизию метрики/данных рядом с результатом для объяснимого пересчёта.

### F21 · P1 при нескольких инстансах · Очистка подготовки может затронуть другой Compose-инстанс

`server/src/dependencies/preparation.ts:13`, `server/src/dependencies/preparation.ts:70`.

Метка владельца Docker-ресурсов строится из внутреннего `config.dataDir`. У разных Compose-развёртываний это одинаковое `/data`, хотя host-каталоги разные. В проверке с fake Docker старт второго инстанса выбрал метку первого и запросил удаление его активного контейнера. На единственном инстансе сценарий не возникает.

**Исправление:** устойчивый instance UUID либо canonical host data root; отдельный тест соседних инстансов на одном daemon.

### F22 · P2 · Удаление соревнования оставляет wheel-наборы на диске навсегда

`server/src/competitions/store.ts:631`, `server/src/dependencies/service.ts:115`, `server/src/dependencies/files.ts:67`.

SQL каскадирует bundles, но директории `dependencies/bundles/<id>` не удаляются и не входят в reconciliation. GC удаляет CAS-путь, однако hardlink в каталоге набора удерживает байты. После полного доступного GC тест сохранил читаемый wheel при отсутствии DB/CAS-записей.

**Исправление:** reconciliation каталогов наборов относительно SQLite, учитывающий ссылки принятых посылок, активную публикацию и прерывание после SQL-delete.

### F23 · P3 · Разные уровни по-разному считают строки requirements

`server/src/dependencies/store.ts:99`, `server/src/dependencies/preparation.ts:89`, `server/src/dependencies/preparation-python.ts:111`.

32 строки комментариев и один пакет проходят API/store, но Python отклоняет запрос как превышение 32 физических строк. Задача уже использует подготовку и её часовую квоту.

**Исправление:** единое определение лимита (физические или содержательные строки), проверяемое до постановки в очередь и показываемое тем же способом в UI.

## Поведение, ограничения и потенциальные риски

### B01 · Подтверждённое поведение, нужна продуктовая семантика: выключение AI-агента действует только на новые запросы

`server/src/routes/ai.ts:505`, `server/src/ai/agent.ts:2846`.

При уже принятом ходе последующие инструменты перепроверяют file/run-права, но не отдельный режим `agent: off`. Изолированный тест подтвердил запись после переключения режима. Если кнопка означает немедленное прекращение агентских действий, это P2-баг; если только запрет новых ходов — это должно быть явно написано. Предпочтительно останавливать ход и проверять актуальное agent-разрешение перед каждым действием.

### D01 · Поставка: соревнования не исполняются в стандартном production k3s

`Dockerfile:68`, `Dockerfile:87`, `scripts/release.py:258`, `server/src/competitions/runner-port.ts:191`, `README.md:516`.

Комнаты используют broker, а соревнования по умолчанию напрямую запускают Docker. Опубликованный app image не включает Docker CLI; стандартный Pod не получает daemon/socket. README честно указывает дополнительное требование Docker, но готового совместимого пути в поставке не найдено. Поэтому это **известное ограничение, усиленное отсутствием capability gate**, а не объявленная здесь скрытая уязвимость.

Улучшение: отдельная поддерживаемая служба выполнения заданий/broker API либо явное отключение неподдерживаемого функционала. Health/UI должны различать готовность комнаты, соревнований и подготовки пакетов. Добавление привилегированного Docker socket в production app не является предлагаемым решением аудита.

### R01 · Высокий приоритет проверки: лимит работы CRDT-разбора применяется после построения индекса

`server/src/collab/gate.ts:291`, `server/src/collab/gate.ts:301`, `server/src/collab/gate.ts:874`.

Конструктор Frame создаёт Map-запись на каждый логический clock структуры до `judge()` и `MAX_WALK`. Байтовый предел входа не эквивалентен пределу логического размера представленных диапазонов. Проверен порядок исполнения кода; исчерпание ресурсов живого сервера не испытывалось, и здесь не заявляется полноценный end-to-end security-тест.

Нужны предварительный бюджет логических элементов/работы, интервальный индекс вместо разворачивания диапазонов и ограниченные регрессионные проверки роста CPU/памяти.

### R02 · Инвентарь окружения может отличаться от закреплённой базы посылки

`server/src/routes/competitions.ts:484`, `server/src/environment-inventory.ts`, `server/src/dependencies/revisions.ts:47`.

Публичная карточка читает mutable tag, менеджер и исполнение удерживают revision. После пересборки одноимённого образа эти источники могут разойтись. Это вывод из двух путей кода; отдельная живая пересборка в аудите не выполнялась. Показывать состав по revisionId, рядом явно обозначать более новую доступную версию.

### R03 · Проверка свободного диска не резервирует весь пик публикации

`server/src/dependencies/service.ts`, `server/src/dependencies/files.ts`.

Во время публикации одновременно существуют скачанный wheel и его CAS-копия. Запас `maxDownloadBytes + 256 MiB` может не покрыть пиковое место при 500 MiB, особенно вместе с посылками/бэкапом. Ошибка диска обрабатывается, но admission обещает больше, чем реально резервирует. Нужны общий бюджет/резервация и fault-injection по этапам; реальный диск до заполнения не доводился.

## Приоритет исправлений

1. **Права и согласованность работы класса:** F01, F02, F03; ограничить работу до выделения памяти в R01. Эти изменения должны иметь отдельные воспроизводящие регрессии.
2. **Достоверность результата соревнования:** F10–F11, F14–F15, F20. Общий принцип — immutable attempt ID, ревизия входов и согласованное состояние UI/API.
3. **Ресурсы и восстановление:** F09, F12–F13, F21–F22, затем F04–F06. Квоты должны относиться к реальному хранилищу/ресурсу, а не к обрезанной проекции.
4. **Возвратить зелёный release gate:** F07–F08. F07 подтверждён Linux CI; повторять только macOS-проверку недостаточно. Отдельно решить D01 до обещания соревнований в стандартной k3s-поставке.
5. **Остальная понятность интерфейса и контракты:** F16–F19, F23, B01 и R02.

Это порядок по типу ущерба, не оценка календарной длительности. Независимые исправления CI можно делать параллельно первому пункту.

## Улучшения, которые устранят классы ошибок

- **Сервер — источник результатов.** Отдельный API лидерборда и монотонная ревизия соревнования/посылок вместо расчёта по пагинированному feed и самодельных fingerprint счётчиков.
- **Явные поколения операций.** Attempt/job ID для исполнения; generation для маршрута и личности; version/epoch для полномочий; revision для метрики, данных и базового окружения.
- **Один контракт долговечности.** Для Yjs, файлов и AI определить момент «сохранено», поведение при EIO и доступность undo. Подтверждение клиенту должно соответствовать тому, что восстановится после перезапуска.
- **Разделить offline-команды и состояния.** Команды требуют порядка/идемпотентности; снимкам требуется последнее значение по ресурсу. Универсальный JSON-дедупликатор не даёт обе гарантии.
- **Единый учёт ресурсов.** Авторитетный census и reservations отдельно от отображаемой страницы; общий бюджет комнат, личных ядер, подготовки и соревнований. Отрицательные health-кэши должны восстанавливаться.
- **Capability-aware интерфейс и health.** Отдельные показатели готовности room runtime, competition runtime, PyPI preparation, диска и фоновых очередей. Пользователь должен узнать об отсутствии исполнителя до отправки файла.
- **CI по режимам поставки.** Оставить быстрые unit/SSR, добавить поддерживаемый Linux smoke стандартного production пути, отдельный opt-in/ночной прогон реальных контейнеров, свежий restore-and-run и offline/reconnect browser E2E. Обычный CI сейчас пропускает Docker-тесты подготовки без специального флага.
- **Наблюдаемость попыток.** Связать request/attempt/revision IDs в журналах; измерять возраст очереди, retries, cleanup failures, retained/orphan bytes, delay сохранения и неуспешные откаты. Текущий общий `/api/health` не объясняет готовность всех подсистем.
- **Упростить зоны высокой связанности.** `control.ts` и несколько экранов объединяют много независимых машин состояний. Выделять обработчики и явные переходы постепенно, вместе с исправлениями, а не предпринимать большой переписанный слой без регрессий.
