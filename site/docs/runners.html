Машины для посылок

Другие машины с Docker — арендованные VM на Vast или серверы вуза — берут посылки соревнований из вашей очереди и считают тетради; ответы и метрика остаются на вашем сервере.

Что это и когда помогает

Машина для посылок — любая машина с Docker, которая исполняет тетради посылок соревнований вашего сервера Colloq: арендованная VM на Vast, сервер вуза, рабочая станция лаборатории. Машина сама приходит к серверу по HTTPS, берёт посылку из общей очереди, исполняет тетрадь в той же одноразовой песочнице без сети, что и сервер, и отправляет результат обратно. Оценивает его сервер: материалы, очередь, скрытые ответы и метрика остаются у него. На машине работает тот же образ colloq-server, только в режиме runner — без сервера, без туннеля и без базы, один контейнер агента colloq-runner.

Машины помогают в трёх случаях:

  • Большое соревнование. Сто участников отправляют тетради в последние минуты, а мест на сервере — несколько. Машины добавляют к ним свои места; очередь остаётся одна и честная по людям, как и без машин (см. очередь).
  • Тетради на видеокарте, которые сервер не потянет. У сервера нет карт или их мало: GPU-посылки возьмут машины с картами, например VM на Vast с двумя RTX 4090.
  • Небольшой сервер. VM вуза на 8 vCPU держит занятие, а не очередь посылок. Переведите «Тетради на этом сервере» в «только метрики» — и сервер будет только оценивать ответы, которые прислали машины, а его ядра останутся занятию (см. ниже).

Для участника почти ничего не меняется: та же страница соревнования, те же пределы времени и памяти, те же исходы. Пока его посылку не может взять ни одно место — машины ещё качают образ среды или данные, или подходящей машины нет на связи, — вместо места в очереди он видит «готовится», а пока сервер считает метрику — «оценивается».

Машины подключает и видит только владелец сервера: в панели они в блоке «Машины для посылок» вкладки «Ресурсы».

Что остаётся на сервере и что видит машина

ГдеЧто
Только на сервереБаза данных, участники и их ключи входа, скрытые ответы (solution.csv), код метрики, счёт и лидерборды, очередь и её порядок. Метрику каждой посылки сервер считает сам, во втором одноразовом контейнере, — и тогда, когда тетрадь исполнила машина.
МашинеТетради посылок, которые она исполняет; открытые данные соревнования; готовые наборы «своих пакетов» его участников — по ним видно, какие пакеты выбрали соперники. Образ среды машина скачивает из реестра сама, по дайджесту, который назвал сервер.
Только доверенной машинеСкрытый тест — входные данные, которые тетрадь читает при проверке вместо открытого примера (см. скрытый тест). По умолчанию машина не доверенная.
НикогдаСкрытые ответы, код метрики, счёт, имена участников, их почта и ключи входа, база данных, токен relay.

Обратно машина присылает файл ответа submission.csv, исполненную тетрадь и отчёт о прогоне. Сервер принимает их как данные участника: проверяет размеры и суммы, раскладывает файлы сам, а тексты для участника — в том числе короткие, при скрытом тесте, — пишет своими словами. Границы подробнее — в разделе «Изоляция и ограничения».

Метрика соревнования с видеокартой считается на сервере в лёгком образе kaggle-base (numpy, pandas, scikit-learn, scipy), а не в GPU-образе соревнования на 10–13 ГБ: метрике нужны две таблицы, а не карта. Образ закрепляется за соревнованием при первой его оценке и дальше не меняется — ни для новых посылок, ни при пересчёте, ни если карту в соревновании потом выключить. Перевести метрику на текущий kaggle-base можно только явно: в редакторе соревнования с картой — строкой «Образ метрики» в разделе «Метрика», а в пульте — кнопкой «Перевести метрику на текущий kaggle-base» у посылки, метрика которой упала, потому что закреплённого образа на сервере больше нет. Тогда пересчитываются все посылки соревнования, а тетради заново не выполняются. Поэтому держите kaggle-base готовым на сервере до первой оценки (KERNEL_PRELOAD=base,kaggle-base): соревнование, первая метрика которого посчиталась без него, остаётся на закреплённых образах самих посылок, как до этой версии; проверка бейслайна на процессоре, до того как включили карту, ничего не закрепляет. Метрика, которая импортирует torch, здесь упадёт как код метрики — «УПАЛА МЕТРИКА», и после правки её можно пересчитать. Соревнование, метрика которого ни разу не считалась с картой, по-прежнему считает её в закреплённом образе посылки.

Подключите машину

  1. В панели откройте вкладку «Ресурсы» и в блоке «Машины для посылок» нажмите «Подключить машину».
  2. Задайте, сколько машин подключится по одному коду, сколько часов код действует (до 24), места на машину (пусто — по ядрам, см. места) и, если нужно, «Доверить машинам скрытый тест» — по умолчанию выключено.
  3. Нажмите «Показать команды». Код покажется один раз — внутри трёх готовых команд. Выполните одну из них: первые две — на самой машине, от root; третью — у себя, из checkout репозитория.
# Docker уже стоит: Linux amd64, Docker Engine 28+; машине с GPU нужен ещё nvidia-container-toolkit
docker run -d --name colloq-runner --restart unless-stopped --stop-timeout 90 \
  -v /var/run/docker.sock:/var/run/docker.sock \
  -v /var/lib/colloq-runner:/var/lib/colloq-runner \
  -e COLLOQ_RUNNER_JOIN='https://colloq.example.edu#<код>' \
  ghcr.io/colloq-edu/colloq-server:X.Y.Z runner

# Голая машина (Ubuntu): ставит Docker и colloq-host, а тот — NVIDIA Container Toolkit
command -v docker || curl -fsSL https://get.docker.com | sh
docker run --rm -v /usr/local/sbin:/host ghcr.io/colloq-edu/colloq-server:X.Y.Z install-host /host
colloq-host runner up https://colloq.example.edu <код>

# VM на Vast, из checkout репозитория (см. ниже)
make vast-runner COUNT=3 CODE=<код> URL=https://colloq.example.edu

Код — 32 шестнадцатеричных знака. В первой команде он стоит в адресе после #: эта часть адреса не уходит в строку запроса. --stop-timeout 90 даёт агенту полторы минуты на остановку: за это время он возвращает серверу посылки, которые держит, и они не считаются потерянными. Код действует для заданного числа машин и не дольше суток. Сервер хранит только его отпечаток, поэтому показать код второй раз нельзя — выпустите новый. Отправляйте его тому, кто ставит машину, а не в общий чат: пока код действует, по нему подключится любая машина, и она увидит тетради участников.

Действующие коды перечислены в блоке под заголовком «Коды подключения»: на сколько машин, сколько уже подключилось, до какого времени код действует и кто его выпустил. «Отменить» закрывает код сразу: по нему больше не подключится ни одна машина, даже та, где команда уже вставлена, а подключившиеся продолжают работать. «Отключить все» отменяет и все действующие коды.

Под командами окно пишет «Ждём первую машину…», а потом называет подключившиеся. Окно можно закрыть: машины появятся в списке сами. Если адрес в командах — loopback этого сервера (localhost), окно предупреждает: машина в другом месте до него не дойдёт, задайте PUBLIC_URL. Подключённая машина сразу начинает скачивать образы сред и данные открытых соревнований, а посылки соревнования берёт, когда для него всё готово (см. готовность). С одного адреса сервер принимает не больше 10 подключений за 10 минут: машины за одним NAT подключайте партиями.

Без панели. Если до панели не добраться — например, на сервер ходят только по SSH через Teleport, — тот же код выпускает на машине сервера colloq-host runner-code. Он печатает код один раз, внутри тех же трёх команд:

colloq-host runner-code --machines 3 --hours 12
colloq-host runner-code --machines 2 --trusted --slots 4 --prefix lab

--machines — сколько машин подключится по коду, от 1 до 100 (по умолчанию 1); --hours — сколько часов код действует, от 1 до 24 (24); --trusted — машины сразу получат скрытый тест; --slots — не больше стольких мест на каждой машине, от 1 до 64; --prefix — имена машин на сервере (lab-1, lab-2…; без него машину называет её имя хоста, и в панели это имя не меняется); --url — адрес, по которому машины придут к серверу (по умолчанию PUBLIC_URL).

Какой образ в командах. Тот, на котором работает сервер: опубликованный выпуск — как ghcr.io/colloq-edu/colloq-server:<версия>, образ из вашего реестра или зеркала — целиком, и тогда colloq-host runner up получает его третьим аргументом. Во втором случае команды make vast-runner нет: арендованные машины берут опубликованный образ, а не ваш.

Закрытый реестр. Первые две команды скачивают образ без входа в реестр, поэтому сначала войдите в него Docker машины, от root, с токеном только на чтение: docker login <реестр>. colloq-host runner up и runner update входят и сами, если им передать COLLOQ_REGISTRY_USER и COLLOQ_REGISTRY_TOKEN, — но только в реестр образа агента, а сами переменные в runner.env не сохраняются. Ядра агент скачивает по дайджесту из реестра, откуда их взял сервер (KERNEL_IMAGE_REPO), с тем входом root, который colloq-host передаёт контейнеру агента: если ядра лежат в другом закрытом реестре, войдите и в него. Агент, запущенный первой командой, этого входа не получает: закрытые ядра он скачает, только когда colloq-host пересоздаст его контейнер первым runner update (см. обновление).

Что нужно машине

  • Linux на x86-64 и Docker Engine 28 или новее. Образ собирается только для amd64.
  • Выделенная машина. Агент держит Docker socket, а это root на машине. Он отдаёт посылкам все карты, какие найдёт, и считает свободную память по всей машине, ничего не зная о комнатах занятий на том же Docker. Поэтому не ставьте его рядом с сервером, на котором идут занятия: colloq-host runner up предупреждает, если находит там контейнер сервера. Вуз одалживает соревнованию машину, которую может отдать целиком.
  • Диск: не меньше 40 ГБ без карт и 120 ГБ с картами — столько, сколько арендовано или куплено. Файловая система на диске показывает на несколько процентов меньше, и проверка оставляет на это 5 %. GPU-ядра занимают около 10–13 ГБ, сверху — кэш данных и пакетов и сами прогоны. Меньший диск машина показывает в панели как «на диске мало места»; когда место кончается, она сама удаляет то, что давно не нужно.
  • Для видеокарт — драйвер NVIDIA 580 или новее и NVIDIA Container Toolkit. GPU-ядра собраны под CUDA 13.0, и на старом драйвере torch карты не видит. colloq-host runner up ставит toolkit сам, через apt, но не драйвер, и сразу говорит, годится ли драйвер. GPU-образ машина проверяет коротким запуском torch на той карте, где есть свободная доля, и не берёт GPU-посылок, пока проверка не прошла: в панели это «драйвер 535, нужен 580+ — GPU-образ не запустится». Если все доли заняты посылками, проверка ждёт и ошибкой не считается. Посылки на процессоре машина при этом берёт.
  • Только исходящие соединения. HTTPS к адресу сервера (PUBLIC_URL; http:// — только для сервера в той же сети), к реестру образов (ghcr.io или ваш) и к индексу пакетов, откуда сервер брал «свои пакеты» участников; если индекс недоступен, машина берёт пакеты у сервера. Входящих портов не нужно. Исходящий прокси и внутренний CA (HTTPS_PROXY, NO_PROXY, NODE_EXTRA_CA_CERTS) передайте вызову colloq-host runner up: он запишет их в /etc/colloq/runner.env. Образы скачивает сам Docker машины, и прокси ему задают отдельно, как на сервере (см. исходящий прокси).
  • Каталог агента — /var/lib/colloq-runner, на хосте и в контейнере по одному пути, с правами 0700; в нём удостоверение машины (runner.json, права 0600) и кэш данных и пакетов. Другой каталог задаёт COLLOQ_RUNNER_STATE — только отдельный, например /srv/colloq-runner: системные каталоги и каталог состояния сервера Colloq агент не примет.

Серверу машины добавляют свои требования к образам. Образ среды соревнования должен быть на сервере, когда тот закрепляет среду за соревнованием — при первом запуске его тетради, обычно при проверке бейслайна, — и когда он готовит «свои пакеты» участников; машины скачивают тот же образ из реестра. Дальше GPU-соревнованию, тетради которого считают только машины (тетради на сервере выключены или у сервера нет карты для посылок), свой образ на сервере для приёма посылок не нужен, когда сошлись три условия: его метрика считается в kaggle-base (тогда на сервере нужен он), ревизия среды есть в реестре, а за последний час на связи была машина с картами, на которую помещается его посылка, — память машины без 2 ГБ вмещает память посылки и ещё 256 МБ, а ядра машины без одного — ядра посылки. Соревнованию, метрика которого осталась на образах самих посылок (его первая метрика посчиталась без kaggle-base, см. метрику), свой образ на сервере нужен, как и раньше, а соревнованию на процессоре — всегда: в нём считается его метрика.

Места, карты и доверие

Места — сколько посылок машина считает одновременно. По умолчанию — авто: столько, сколько машина сама предлагает по своим ядрам и памяти. Себе и Docker она оставляет одно ядро и 2 ГБ памяти, а посылку берёт, только если пределы соревнования — ядра и память, и ещё 256 МБ сверху — помещаются в то, что осталось. Своё число, от 1 до 64, задают в окне подключения («Места» → «на машину»), пунктом «Места…» в меню строки или на странице машины; пусто — снова авто. Свободное место машины сервер занимает в том же честном порядке очереди, что и свои места.

Места панель считает в посылках того размера, какие есть: машина на 61 vCPU предлагает 60 мест, по ядру на посылку, а посылок по 2 ядра на ней по ядрам помещается 30 — и меньше, если их память, с 256 МБ сверху на каждую, не помещается 30 раз в то, что осталось от памяти машины; панель пишет меньшее число. Пульт соревнования и строка «Где считается» в редакторе считают места в посылках самого соревнования, список машин — в посылках, которые сейчас ждут или идут, а без них — в самой большой посылке открытого соревнования.

Карты. Машина отдаёт посылкам все свои карты — в отличие от сервера, где карты для посылок отмечает владелец. Сколько посылок делят одну карту, задаёт пункт «Посылок на карту…» в меню машины; пусто — как на сервере, в блоке «Видеокарты для посылок» («Посылок на одной карте»). Срез видеопамяти — память карты, делённая на это число, и держат его так же, как на сервере: ограничением PyTorch изнутри и сторожем снаружи (см. видеокарту для посылок). Карта ускоряет только то, что тетрадь сама переносит на CUDA, — модель и тензоры: тетрадь, написанная для процессора, и на машине с картой считает на процессоре. Машина без карт GPU-посылок не берёт.

Доверенная машина — единственная, что получает скрытый тест. Доверие дают при подключении («Доверить машинам скрытый тест») или потом — пунктом «Доверенная» в меню строки или на странице машины. Снятое доверие возвращает в очередь её прогоны со скрытым тестом, обрывает его скачивание и удаляет скрытый тест с машины. Пока доверенной машины нет, посылки со скрытым тестом считает сервер, если тетради на нём включены, а иначе они ждут: «ждёт доверенную машину: скрытый тест». Арендованной машине скрытый тест лучше не доверять: всё, что на ней лежит, видит хозяин хоста.

Готовность. Для каждого соревнования, которое открыто, откроется в ближайшие сутки или где ждут посылки, машина заранее скачивает образ среды, данные и, если она доверенная, скрытый тест, сверяя суммы. Посылки соревнования она берёт, только когда всё на месте; пакеты участников качает тоже заранее, а недостающие докачивает при подготовке посылки — время скачивания не входит во время тетради. В строке это выглядит как «образ ↓ 45 %», «данные ✓», «скрытый тест — только доверенным». Соревнование, среда которого собрана на этом сервере, помечено «считает только сервер»: её образа нет в реестре, и машины её не получат (см. среды из реестра). Подготовка, которая не удалась, называет причину: «драйвер 535, нужен 580+ — GPU-образ не запустится», «torch не видит CUDA — GPU-образ не запустится», «образ не скачался», «данные не скачались или не сошлись суммы», «на диске мало места».

Страница машины (пункт «Страница машины» в меню): что машина сообщила о себе — ядра, память, диск, карты, драйвер, Docker; её места, посылки на карту и доверие; готовность к каждому соревнованию; что она считает сейчас, с кнопкой «Остановить посылку» — остановка доходит до машины со следующим её откликом, до 15 с, а посылку, которая уже отдаёт или отправляет результат, с машины не снять; последние 50 событий и счётчики — сколько посылок она посчитала, сколько было потерь и отказов.

Пульт соревнования группирует исполнителей: «Сервер» и каждая машина со своими местами и картами; у идущей посылки видно, на какой машине и карте она считается, а метрики сервера шапка пульта считает отдельно — «МЕТРИКИ · 2 ИЗ 2». У ждущей посылки стоит причина, если та ждёт не просто своей очереди: «машины качают образ», «машины качают данные», «ждёт доверенную машину: скрытый тест», «ждёт карту: её нет ни здесь, ни на машинах», «не помещается ни на одну машину на связи», «некому считать: сервер считает только метрики, а машины работу не берут», «вернулась: vast-1 замолчала». Посылка, тетрадь которой посчитана и ждёт метрики, — «оценивается».

«Работают сейчас» во вкладке «Ресурсы» показывает соревнование, тетради которого идут на машинах, отдельной строкой — с машинами под ней и памятью «здесь 0 МБ»: посылки на машинах памяти сервера не занимают, здесь остаются только их строки в очереди и метрика пришедших ответов. Кнопка «Остановить посылки на машинах» снимает их: на машине посылка останавливается со следующим её откликом, до 15 с, а участник попытку не тратит.

Редактор соревнования в строке «Где считается» говорит, кто возьмёт его посылки: сервер, сколько машин и мест, какие машины ещё готовятся и какие не подходят. Он же предупреждает, если среду собрали на этом сервере («только этот сервер») или если посылки со скрытым тестом некому считать.

Тетради на этом сервере и оценки

Над списком машин — два поля формы «Ресурсы»; сохраняет их кнопка формы «Сохранить изменения».

  • «Тетради на этом сервере». По умолчанию — «считать и здесь»: тетради считают и сервер, и машины. С «только метрики» тетради считают только машины, сервер оценивает пришедшие ответы, а его ядра остаются занятию; шкала памяти той же вкладки отводит соревнованиям тогда только места оценок. Если при «только метрики» на связи нет ни одной машины, посылки ждут, и блок так и пишет, а сохранить такое положение форма даёт только после вопроса. Посылки среды, собранной на этом сервере, и посылки со скрытым тестом без доверенной машины при «только метрики» считать некому — редактор соревнования предупреждает об этом.
  • «Оценок одновременно» — сколько метрик сервер считает одновременно: от 1 до 8, по умолчанию 2. Метрика — до 2 минут и 2 ГБ на ответ. Метрики ответов с машин и пересчёты идут по этим местам, а не по местам тетрадей. Память у тетрадей и метрик сервера общая: когда её хватает только на одно, первым идёт то, что ждёт дольше (присланное вовремя — раньше опоздавшего); ответ с машины ждёт с отправки своей тетради, пересчёт — с той минуты, когда его попросили. Приостановленная очередь держит новые тетради и пересчёты, но метрики ответов, которые уже вернулись с машин, идут и под паузой. На всплеске посылок, которые считают машины, узкое место — именно эти места: на сервере со свободными ядрами и памятью поднимите их число (см. проверку на Vast).

Обновление

Машина берёт новые посылки, только пока её код совпадает с кодом сервера — сборкой агента из того же выпуска. Выпуск, который не трогает код машин, оставляет их в работе как есть. Выпуск, который его меняет, переводит их в состояние «устарела»: начатые посылки они досчитывают, новых не берут, а в строке написано, например, «код 0.23.0, сервер 0.24.0 — новых посылок не берёт». Поэтому порядок такой: сначала сервер, потом машины.

# 1. Сервер, как обычно
colloq-host update ghcr.io/colloq-edu/colloq-server:X.Y.Z

# 2. Машины на Vast — все машины этого сервера, из checkout репозитория
make runners-update URL=https://colloq.example.edu

#    или одна машина с colloq-host, по SSH, от root
colloq-host runner update

colloq-host runner update узнаёт версию сервера по его /api/health, скачивает её образ, осушает машину — начатые посылки досчитываются, новых она не берёт — и запускает агента на новом образе; заодно обновляется и сам colloq-host. Если сама машина до /api/health не достаёт, версию называет агент, но только по синхронизации, сделанной уже после начала обновления: её команда ждёт до минуты (COLLOQ_RUNNER_FRESH_SEC), а без неё просит назвать версию. Осушение ждёт не дольше самого длинного прогона, какой допускает протокол (COLLOQ_RUNNER_DRAIN_SEC, по умолчанию 15 720 с). С --now оно не ждёт: начатые посылки возвращаются в очередь и считаются заново — без потерь и без траты попыток участников. Версию можно назвать и явно: colloq-host runner update 0.24.0. Образ без агента — выпуск до машин для посылок, например после отката сервера, — runner update и runner up отклоняют раньше, чем что-нибудь осушат или запустят: работающий агент остаётся на прежнем образе.

Машина, подключённая первой командой (docker run), colloq-host не имеет. Поставьте его из того же образа — docker run --rm -v /usr/local/sbin:/host <образ> install-host /host, — и первый же colloq-host runner update, leave, status или logs примет её контейнер: прочитает из него образ, адрес сервера, код и каталог и дальше ведёт машину так же, как поставленную через runner up.

make runners-update делает то же на всех машинах Vast сразу. На каждой машине обновление идёт в фоне и переживает обрыв SSH, а повторный вызов подхватывает уже идущее. Сначала команда до минуты ждёт, пока агент каждой машины заново синхронизируется с сервером: машину, код которой сервер в этой синхронизации признал своим, она не трогает (FORCE=1 — обновить всё равно), а машину без такого свежего ответа обновляет — дальше решает colloq-host на ней. NOW=1 — то же, что --now; VERSION= — одна версия для всех.

Перезапуск сервера посылки на машинах не обрывает: машины досчитывают их и отправляют результаты, когда сервер снова на связи, а первые 3 минуты после старта сервер ни одну машину не считает пропавшей. Обновляйтесь всё же между соревнованиями, а если не вышло — обновите машины сразу после сервера. Сами себя машины в этой версии не обновляют.

Отключение и уход

  • colloq-host runner leave на машине (машине, подключённой первой командой, сначала поставьте colloq-host, см. обновление): она досчитывает начатое, новых посылок не берёт, отзывает себя на сервере и удаляет контейнер агента. Кэш данных и пакетов остаётся в /var/lib/colloq-runner — удалите каталог, чтобы освободить место; образы ядер остаются в Docker машины (colloq-revision:<id>), их удаляет docker image rm или docker image prune -a. Уход кончается ответом сервера: если сервер молчит 10 минут, colloq-host перестаёт ждать и говорит об этом, а агент продолжает уходить — новых посылок не берёт и отзовёт себя, как только сервер ответит. Вернуть машину можно только новым кодом: со старым она не подключится, даже если on-start Vast повторит его при загрузке.
  • make runners-down URL=https://colloq.example.edu — то же для машин Vast этого сервера, после чего их VM удаляются вместе с дисками; сначала команда спрашивает подтверждения. Машину, которая не ушла (например, её сервер молчал 10 минут), команда всё равно удаляет и говорит, что сервер её ещё числит: отключите её в панели. С NOW=1 VM удаляются сразу, без ожидания: сервер потеряет машину через 3 минуты молчания и посчитает её посылки заново, а в списке она останется, пока её не отключат.
  • «Отключить» в меню строки (или «Отключить все» под списком): сервер сразу перестаёт принимать секрет машины. Её посылки возвращаются в очередь без потери лимита, поздние ответы не принимаются, а агент на следующем запросе удаляет скрытый тест и останавливается, чтобы больше не запускаться. Арендованную VM это не удаляет, и она тарифицируется, пока её не удалят. Сама машина обратно не подключится, но код, с которым она пришла, действует, пока не истечёт, не израсходуется или пока его не отменят в списке «Коды подключения»; «Отключить все» отменяет и все действующие коды.

Участникам уход машины ничего не стоит: посылки, которые она не досчитала, считаются заново на другом месте, а сам уход не тратит ни дневной нормы, ни попыток. Отключённая или ушедшая машина остаётся в списке ещё 30 дней, потом сервер удаляет её вместе с её событиями.

Если машина подводит

  • Молчит. Машина, которую сервер не слышит 3 минуты, теряет свои прогоны: они возвращаются в очередь на своё место — раньше тех, кто пришёл после них, — и запускаются снова, на другой машине или на сервере. Участник читает: «Машина, на которой шла посылка, перестала её выполнять. Посылка вернулась на своё место в очереди и запустится снова; попытка не потрачена». Пропавшей машину сервер считает, только если знает, что дорога к машинам работает: другая машина отвечала в последнюю минуту или прошла его собственная проверка своего адреса. Если пропала сама дорога — упал туннель или прокси сервера, — ничего не теряется до 15 минут, а когда дорога возвращается, каждая машина снова получает полные 3 минуты.
  • Отказывается. Машина, которая не может запустить посылку — нет образа, данных или пакетов, не хватает диска, памяти или доли карты, — возвращает её до старта контейнера. Посылка сразу уходит на другое место, а эта машина не получит её 10 минут. Участнику отказ ничего не стоит.
  • Теряет снова и снова. Посылку, которую потеряли три разные машины или шесть раз — любые, сервер больше в очередь не ставит: она заканчивается сбоем сервера — «Это сбой сервера, а не вашей тетради; попытка не потрачена» — и не тратит ни нормы, ни потолка упавших; исполнить её заново можно из пульта. Так же заканчивается посылка, от которой отказались три разные машины.
  • Зависает. Прогон, который тянется дольше своего предела — 10 минут на подготовку, время тетради, ещё 2 минуты и 10 минут на отправку результата, — сервер отзывает и считает потерянным, даже если машина продолжает отвечать.
  • Карантин. Три потери или пять отказов на одной машине за 30 минут — и сервер сам её осушает: она досчитывает начатое и больше ничего не берёт, а над списком появляется баннер. Прогоны, потерянные разом, — например, все прогоны одного перезапуска агента, — это одна потеря, и считаются только потери после старта контейнера. Посмотрите события на странице машины и, устранив причину, нажмите «Вернуть в работу»: счёт карантина начнётся заново.
  • Перезапуск агента. Если агент упал или машина перезагрузилась, Docker запускает его снова. При старте агент сначала убеждается, что прогоны его прошлой жизни уже не идут, и удаляет их контейнеры; результаты, которые он успел записать, всё равно отправляет, а остальные его прогоны сервер сразу считает потерянными и ставит в очередь заново. Остановленный агент (docker stop, colloq-host runner update --now) сначала возвращает их серверу, без потерь. docker kill colloq-runner для Docker — остановка вручную: такой агент сам не перезапускается, его прогоны сервер вернёт в очередь через 3 минуты молчания, а контейнеры посылок остаются на машине, пока агента не запустят снова — docker start colloq-runner или тем же colloq-host runner up, которым машину подключали; при старте он их уберёт.

Машины на Vast

Из checkout репозитория, с VAST_TOKEN и SSH-ключом в .env, как для make vast-vm:

make vast-runner COUNT=3 CODE=<код> URL=https://colloq.example.edu
make vast-runner COUNT=2 GPU="RTX 4090" GPUS=2 DISK=150 CODE=<код> URL=https://colloq.example.edu

Команда арендует COUNT VM, от 1 до 16, тем же путём, что make vast-vm: с теми же фильтрами предложений (GPU=, GPUS=, GPU_RAM=, CPU=, RAM=, DISK=, MAX_PRICE=) и тем же порогом Max CUDA 13.0. Сначала она пишет, что арендует и сколько самое большее платит за час каждой машины (MAX_PRICE), и спрашивает подтверждения (FORCE=1 — без вопроса); найденное предложение и его цену каждая машина называет уже после этого. Машины арендуются по очереди — каждая берёт самое дешёвое подходящее предложение — и загружаются одновременно; каждая ждёт, пока её агент подключится. Код должен быть рассчитан хотя бы на COUNT машин; URL= можно один раз записать в .env как VAST_RUNNER_URL.

Диск по умолчанию — 120 ГБ, нижняя граница для машины с картами: VM без карт на Vast не бывает, а машине с картами нужны GPU-ядра. Машина для посылок на процессоре — это VM подешевле с нужным числом ядер (CPU=), и её карта тоже возьмёт GPU-посылки.

В on-start арендованной VM — только адрес сервера и код: ни токена relay, ни других ключей. On-start видит оператор хоста, и Vast хранит его в консоли, а код ничего не стоит не позже чем через сутки или когда подключились все машины, на которые его выпустили (команда из окна подключения ставит COUNT равным их числу). Версию образа машина узнаёт у сервера, поэтому после обновления сервера новый on-start не нужен — нужен make runners-update.

Машины помечаются на Vast меткой colloq-runner (с NAME= — colloq-runner-<NAME>), и по ней их находят make runners-update и make runners-down. Каждую машину они сначала спрашивают по SSH, какому серверу она служит; с URL= берутся только машины этого сервера, без него — все машины аккаунта с этой меткой.

Оплата — ваша. Машины тарифицируются на вашем аккаунте Vast, пока их не удалят. В том числе те, что арендовались, но не подключились (сервер не ответил, у кода кончились подключения): их нет ни в одном списке машин. Команда в конце называет каждую такую машину и печатает команду её удаления, а с DESTROY_UNJOINED=1 удаляет их сама. Машина, отключённая в панели, тоже тарифицируется, пока её не удалят — make runners-down или в консоли Vast.

Среды из реестра и GPU-ядра

Образ среды машина скачивает не у сервера, а из реестра — по дайджесту, который сервер записал, когда сам получил этот образ, — и перед запуском сверяет его слои с образом сервера. Поэтому машины считают только те среды, образ которых сервер скачал из реестра. base и kaggle-base публикуются с каждым выпуском; GPU-ядра base-gpu и kaggle-gpu — отдельной командой make kernel-publish на машине с картой, при выпуске (RELEASING.md). Сервер берёт их из реестра, если они перечислены в KERNEL_PRELOAD, например KERNEL_PRELOAD=base,kaggle-base,base-gpu,kaggle-gpu.

Среду, собранную или изменённую на этом сервере, в этой версии считает только сервер: её образа нет в реестре. В списке машин такое соревнование помечено «считает только сервер», в редакторе — «только этот сервер». С KERNEL_IMAGE_REPO=none сервер собирает все среды сам, и машинам считать нечего. Так же остаётся на сервере GPU-ядро, которое он собрал сам, пока ядро его версии ещё не было опубликовано; как перейти на опубликованное — в том же разделе RELEASING.md.

Проверено на Vast

14 октября 2026 года, в два захода, на двух сборках этой версии до выпуска. Сервер — VM на Vast (61 vCPU, 86 ГБ, RTX A2000 на 6 ГБ) за relay, с «Тетради на этом сервере» в положении «только метрики»: каждый запрос машин шёл через relay. В первом заходе машина была одна — на той же VM, что и сервер (только для опыта: в работе машина должна быть отдельной); во втором к ней добавилась отдельная VM с 1 × RTX 4090 на 24 ГБ, 35 vCPU и драйвером 580.95.05.

52 посылки разомвсе получили оценку за 60 с на двух машинах; вердикт — медиана 44 с, последний 59 с
Эталон GPU-соревнования по распознаванию букв, по 2 посылки на A20006 из 6 оценены, около 90 с каждая — на процессоре: эталон ничего не переносит на CUDA; проверка бейслайна на доле карты — 18 с

Узкое место всплеска — метрики на сервере. В первом заходе, с одной машиной и «Оценок одновременно» на 2, хвост всплеска из 30 посылок ждал метрик (по 4,6 с на ответ), и последний вердикт пришёл через 96 с. Всплеск из 52 посылок во втором заходе закончился за минуту при 8, но у него были ещё две машины и новая сборка, поэтому, сколько дали одни эти 8, два всплеска не показывают. Если у сервера есть свободные ядра и память, поднимите «Оценок одновременно» перед соревнованием с машинами. И помните про CUDA: эта эталонная тетрадь ничего не переносит на карту, поэтому и на машине с картой считает на процессоре — во втором заходе по 80 с на посылку.

Что сделалиЧем кончилось
Убили процесс агента посреди 10 прогонов (kill -9 внутри контейнера)Docker запустил агента снова; тот убрал 10 контейнеров посылок прошлой жизни и сообщил, что их прогонов больше не держит. Сервер сразу вернул их в очередь, машина на карантин не ушла, все 10 оценены по одному разу.
Перезапустили сервер посреди прогоновМашина продолжала прогоны и, пока сервер поднимался, повторяла запросы (relay отвечал 404); все 10 результатов приняты после старта, потерь нет.
Оборвали туннель relay на 4 минуты посреди прогоновНи один прогон не потерян: дорога к машинам пропала, и сервер ждал. Прогоны досчитались, отправка повторялась, все 6 результатов приняты, когда туннель вернулся.
Отрезали одну машину от relay, пока другая была на связи, но осушенаПримерно через 190 с её 8 прогонов потеряны. Они ждали, пока вторую машину не вернули в работу, и посчитались на ней; 8 поздних результатов вернувшейся машины сервер отбросил. Каждая посылка оценена один раз, карантина не было.
Отключили машину посреди прогонов, потом подключили новым кодомАгент получил 401, бросил прогоны, удалил их контейнеры и остановился, выключив свой перезапуск; 4 посылки вернулись в очередь без потерь. По новому коду машина пришла как новая, и 4 посылки оценены.
Сняли доверие с машины, которая скачала скрытый тестСкрытый тест удалён с машины, посылка с ним ждала «ждёт доверенную машину: скрытый тест»; после нового доверия тест скачан заново, посылка оценена.
Остановили посылку, которая шла на машинеКонтейнер посылки исчез через 1,3 с, посылка отменена.
Обновили сервер на новый код машинСтарая машина стала «устарела» и посылок не брала; colloq-host runner update осушил, заменил и снова подключил её за 6,7 с, и ждавшие посылки оценены.

Найденное репетицией исправлено до выпуска. Одна остановка агента посреди 10 прогонов сразу уводила машину на карантин; сборка второго захода считает её одной потерей, и это видно по агенту, убитому в том заходе (выше). Три исправления сделаны уже после обеих сборок, и на Vast их не проверяли: панель писала места по ядрам машины, а не по посылкам соревнования; GPU-соревнование требовало на сервере свой образ на 13 ГБ, даже когда тетради считали только машины; сервер, обновлённый прежним colloq-host, называл в командах опубликованный образ, даже работая на своём. Ещё репетиция показала, что docker kill — остановка вручную, а не сбой (см. сбои).

Чего машины пока не делают

  • Не готовят «свои пакеты» участников: наборы готовит сервер (на Docker-пути ему нужен Docker Engine 28 или новее), машины только скачивают готовые.
  • Не запускают ядра комнат: занятия идут на сервере, как и раньше.
  • Не обновляются сами: после обновления сервера нужен make runners-update или colloq-host runner update.
  • Не подписывают запросы. Машина предъявляет свой секрет в заголовке, а TLS заканчивается на обратном прокси или relay перед сервером: кто управляет ими, может прочитать секреты машин (см. изоляцию).
  • Не продолжают прогон после перезапуска агента: такой прогон считается заново.
  • Одна машина служит одному серверу. Арендовать машины из панели нельзя — только make vast-runner или руками.
  • Сервер в Kubernetes (Helm-чарт) машин для посылок в этой версии не подключает: блока «Машины для посылок» в его панели нет.
