Submission machines

Other Docker machines, rented Vast VMs or university servers, take competition submissions from your queue and run the notebooks; the answers and the metric stay on your server.

What it is and when it helps

A submission machine is any machine with Docker that runs the notebooks of your Colloq server's competition submissions: a rented Vast VM, a university server, a lab workstation. The machine comes to the server by itself over HTTPS, takes a submission from the shared queue, runs the notebook in the same throwaway sandbox with no network that the server uses, and sends the result back. The server scores it: the materials, the queue, the hidden answers and the metric stay with it. The machine runs the same colloq-server image in its runner mode — no server, no tunnel and no database, just one agent container, colloq-runner.

Colloq server: materials, queue, answers, metric↑ HTTPS — the machine calls inSubmission machine: the colloq-runner agent↓ the machine's Docker socket
Submission ASubmission BSubmission C

Machines help in three cases:

  • A big competition. A hundred participants send notebooks in the last minutes, and the server has a few places. The machines add places of their own; the queue stays one queue, fair per person, as without them (see the queue).
  • GPU notebooks the server cannot hold. The server has no cards, or too few: GPU submissions go to machines with cards, such as Vast VMs with two RTX 4090s.
  • A small server. A university VM with 8 vCPU holds the class, not the submission queue. Set Notebooks on this server to metrics only, and the server only scores the answers the machines send back, while its cores stay with the class (see below).

For a participant almost nothing changes: the same competition page, the same time and memory limits, the same outcomes. While no place can take their submission yet — the machines are still downloading its environment image or data, or no machine that fits is online — they see “getting ready” instead of a place in the queue, and “being scored” while the server runs the metric.

Only the server's owner connects and sees the machines: in the panel they are in the Machines for submissions block of the Resources tab.

What stays on the server and what a machine sees

WhereWhat
Only on the serverThe database, the participants and their sign-in keys, the hidden answers (solution.csv), the metric code, scores and leaderboards, the queue and its order. The server runs the metric of every submission itself, in the second throwaway container — also when a machine ran the notebook.
To a machineThe notebooks of the submissions it runs; the competition's open data; the ready sets of its participants' own packages — they show which packages rivals chose. The machine pulls the environment image from the registry itself, by the digest the server named.
Only to a trusted machineThe hidden test: the input the notebook reads during the check instead of the open sample (see the hidden test). A machine is not trusted by default.
NeverThe hidden answers, the metric code, scores, participants' names, emails and sign-in keys, the database, the relay token.

Back from the machine come the answer file submission.csv, the executed notebook and a report of the run. The server takes them as participant data: it checks their sizes and checksums, lays the files out itself, and writes the texts a participant reads — the brief ones under a hidden test too — in its own words. More on the boundaries under Isolation and limits.

The metric of a competition with a GPU runs on the server in the light kaggle-base image (numpy, pandas, scikit-learn, scipy), not in the competition's 10–13 GB GPU image: a metric needs two tables, not a card. The image is pinned to the competition at its first metric and does not change after that — neither for new submissions nor on a rescore: the metric moves to the current kaggle-base only when asked to, and then every submission of the competition is rescored. So keep kaggle-base ready on the server before the first metric (KERNEL_PRELOAD=base,kaggle-base): a competition whose first metric ran without it stays on the submissions' own pinned images, as before this version. A metric that imports torch fails here as metric code — Metric failed — and can be rescored once fixed. A competition without a GPU still scores in the submission's pinned image.

Connect a machine

  1. In the panel, open the Resources tab and, in the Machines for submissions block, press Connect a machine.
  2. Set how many machines join on one code, how many hours the code is valid (up to 24), the places per machine (empty: by cores, see places) and, if needed, Trust the machines with the hidden test, which is off by default.
  3. Press Show the commands. The code is shown once, inside three ready commands. Run one of them: the first two on the machine itself, as root; the third on your own computer, from a checkout of the repository.
# Docker is installed: Linux amd64, Docker Engine 28+; a GPU machine also needs nvidia-container-toolkit
docker run -d --name colloq-runner --restart unless-stopped \
  -v /var/run/docker.sock:/var/run/docker.sock \
  -v /var/lib/colloq-runner:/var/lib/colloq-runner \
  -e COLLOQ_RUNNER_JOIN='https://colloq.example.edu#<code>' \
  ghcr.io/colloq-edu/colloq-server:X.Y.Z runner

# A bare machine (Ubuntu): installs Docker and colloq-host, which installs NVIDIA Container Toolkit
command -v docker || curl -fsSL https://get.docker.com | sh
docker run --rm -v /usr/local/sbin:/host ghcr.io/colloq-edu/colloq-server:X.Y.Z install-host /host
colloq-host runner up https://colloq.example.edu <code>

# Vast VMs, from a checkout of the repository (see below)
make vast-runner COUNT=3 CODE=<code> URL=https://colloq.example.edu

The code is 32 hexadecimal characters. In the first command it stands in the address after #: that part of the address never goes into a request line. The code is valid for the number of machines you set and for a day at most. The server keeps only its fingerprint, so the code cannot be shown a second time — mint a new one. Send it to whoever sets the machine up, not to a group chat: while the code is valid, any machine joins with it, and that machine sees participants' notebooks.

Under the commands the window says Waiting for the first machine… and then names the machines as they join. You can close the window; the machines appear in the list by themselves. A machine that has joined starts downloading the environment images and the data of open competitions at once, and takes a competition's submissions once everything for it is ready (see readiness). The server accepts at most 10 joins from one address in 10 minutes: join machines behind one NAT in batches.

Without the panel. When the panel is out of reach — for example, the server is reached over SSH through Teleport only — colloq-host runner-code on the server's machine mints the same code. It prints the code once, inside the same three commands:

colloq-host runner-code --machines 3 --hours 12
colloq-host runner-code --machines 2 --trusted --slots 4 --prefix lab

--machines is how many machines join on the code, 1 to 100 (1 by default); --hours, how many hours it is valid, 1 to 24 (24); --trusted gives the machines the hidden test from the start; --slots caps the places on each machine, 1 to 64; --prefix names the machines on the server (lab-1, lab-2…; without it a machine is named by its host name, and you can rename it on its page); --url is the address the machines reach the server at (PUBLIC_URL by default).

Which image the commands name. The one the server runs: a published release as ghcr.io/colloq-edu/colloq-server:<version>, an image from your own registry or mirror in full. In the second case there is no make vast-runner command: rented machines take the published image, not yours. For a private registry, pass COLLOQ_REGISTRY_USER and COLLOQ_REGISTRY_TOKEN (a read-only token) to colloq-host runner up: the machine's Docker logs in to the image's registry, and the agent pulls kernels from that same registry with the same login.

What a machine needs

  • Linux on x86-64 and Docker Engine 28 or newer. The image is built for amd64 only.
  • A dedicated machine. The agent holds the Docker socket, which is root on the machine. It gives every card it finds to submissions and counts free memory over the whole machine, knowing nothing of class rooms on the same Docker. So do not put it next to a server that runs classes: colloq-host runner up warns when it finds a server container there. A university lends the competition a machine it can give over whole.
  • Disk: at least 40 GB without cards and 120 GB with them. A CPU kernel takes about a gigabyte, the GPU kernels about 10–13 GB, and the cache of data and packages and the runs themselves come on top. A smaller disk shows in the panel as low on disk; when space runs out, the machine removes what has not been needed for a long time by itself.
  • For GPUs, an NVIDIA driver of 580 or newer and NVIDIA Container Toolkit. The GPU kernels are built for CUDA 13.0, and on an older driver torch does not see the card. colloq-host runner up installs the toolkit itself, through apt, but not the driver, and says right away whether the driver will do. The machine checks a GPU image with a short torch run on the card and takes no GPU submissions until that check passes: the panel then says driver 535, 580+ needed: the GPU image will not start. It still takes CPU submissions.
  • Outbound connections only. HTTPS to the server's address (PUBLIC_URL; http:// only for a server on the same network), to the image registry (ghcr.io or yours) and to the package index the server took participants' own packages from; when the index cannot be reached, the machine takes the packages from the server. No inbound port is needed. Pass an outbound proxy and an internal CA (HTTPS_PROXY, NO_PROXY, NODE_EXTRA_CA_CERTS) to the colloq-host runner up call: it writes them to /etc/colloq/runner.env. Images are pulled by the machine's Docker itself, which gets its proxy separately, as on the server (see the outbound proxy).
  • The agent's directory is /var/lib/colloq-runner, at the same path on the host and in the container; it holds the machine's identity (mode 0700) and the cache. COLLOQ_RUNNER_STATE names another one — a directory of its own only, such as /srv/colloq-runner: the agent refuses system directories and the state directory of a Colloq server.

For the server machines add one requirement: it holds the environment image of every competition whose submissions the machines run — it accepts and pins submissions by that image, and the machines pull the same image from the registry. For a GPU competition that is a GPU kernel, about 10–13 GB of the server's disk, even if the server runs no notebooks itself, plus kaggle-base for the metric.

Places, cards and trust

Places are how many submissions a machine runs at once. By default, auto: as many as the machine offers by its own cores and memory. It keeps one core and 2 GB of memory for itself and Docker, and takes a submission only when the competition's limits — the cores and the memory, plus 256 MB on top — fit into what is left. A number of your own, 1 to 64, is set in the connect window (Places → per machine), with Places… in the row's menu, or on the machine's page; empty is auto again. The server fills a machine's free places in the same fair queue order as its own.

Cards. A machine gives every card it has to submissions — unlike the server, where the owner ticks the cards for submissions. How many submissions share one card is set with Runs per GPU… in the machine's menu; empty means as on the server, under GPUs for submissions (Runs per card). The share of video memory is the card's memory divided by that number, and it is held as on the server: by the PyTorch cap inside and the watchdog outside (see a card for submissions). A machine without cards takes no GPU submissions.

A trusted machine is the only kind that gets the hidden test. Trust is given when connecting (Trust the machines with the hidden test) or later, with Trusted in the row's menu or on the machine's page. Taking trust away sends its runs with the hidden test back to the queue and purges the hidden test from the machine. While no machine is trusted, submissions with the hidden test are run by the server when its notebooks are on, and wait otherwise: waiting for a trusted machine: hidden test. Better not trust a rented machine with the hidden test: whoever runs the host sees everything on it.

The list of machines and the console

The Machines for submissions block shows a summary on top — how many machines are online, how many places and cards they have — and below it a row per machine: its state, resources, places (busy of how many), readiness and a menu.

StateWhat it means
onlineIt answers, its code matches the server's, and it takes submissions.
silentNot heard for more than 3 minutes (silent 4 min). If the way to the machines works, its runs go back to the queue for others to run; no quota is spent (see failures).
outdatedIts code differs from the server's: it finishes the submissions it holds and takes no new ones (see updating).
drainingIt finishes what it holds and takes no new submissions: it was drained with Drain in the menu, or it is leaving or updating by itself. Resume puts it back to work.
quarantinedThe server stopped giving it submissions by itself after a run of losses or declines; a banner says so above the list.
disconnectedThe owner disconnected it, and the server no longer accepts its secret.
leftIt left on its own: colloq-host runner leave.

Readiness. For every competition that is open, opens within a day or has waiting submissions, the machine downloads the environment image, the data and, when trusted, the hidden test in advance, checking the checksums. It takes a competition's submissions only once everything is in place; participants' packages are downloaded in advance too, and a missing one is fetched while the submission is prepared — download time is not counted in the notebook's time. In the row this reads as image ↓ 45%, data ✓, hidden test: trusted machines only. Only this server runs it marks a competition whose environment was built on this server: its image is not in the registry, and machines never get it (see environments from the registry). Preparation that failed names its reason: driver 535, 580+ needed: the GPU image will not start, torch sees no CUDA: the GPU image will not start, the image did not download, the data did not download, or its checksums did not match, low on disk.

The machine's page (Machine page in the menu): what the machine said about itself — cores, memory, disk, cards, driver, Docker; its places, runs per GPU and trust; its readiness for each competition; what it runs now, with Stop the submission; the last 50 events, and counters of the submissions it ran, its losses and its declines.

The competition console groups the executors: This server and each machine with its places and cards; a running submission shows which machine and card it runs on. A waiting submission carries a reason when it waits for more than its turn: machines are downloading the image, machines are downloading the data, waiting for a trusted machine: hidden test, waiting for a GPU: none here or on the machines, nobody to run it: this server only scores, and no machine takes work, back: vast-1 went silent. A submission whose notebook has run and waits for its metric is being scored.

Running now on the Resources tab shows a competition whose notebooks run on machines as a row of its own — with the machines under it and its memory as “0 MB here”: submissions on machines hold none of the server's memory; only their rows in the queue and the metric of the answers that came back stay here.

The competition editor, in its Runs on line, says who will take the competition's submissions: this server, how many machines and places, which machines are still preparing and which do not fit. It also warns when the environment was built on this server (this server only) or when nobody can run the submissions with the hidden test.

Notebooks on this server, and scores

Above the list of machines are two fields of the Resources form; the form's Save changes saves them.

  • Notebooks on this server. Run them here too (the default): both the server and the machines run notebooks. Metrics only: only the machines run notebooks, the server scores the answers that come back, and its cores stay with the class. If no machine is online under metrics only, submissions wait, and the block says so. Submissions of an environment built on this server, and submissions with the hidden test while no machine is trusted, have nobody to run them under metrics only — the competition editor warns about that.
  • Scores at once: how many metrics the server runs at once, 1 to 8, 2 by default. A metric takes up to 2 minutes and 2 GB per answer. The metrics of answers from the machines and rescores use these places, not the notebook places.

Updating

A machine takes new submissions only while its code matches the server's — the agent's build from the same release. A release that leaves the machines' code alone keeps them working as they are. A release that changes it makes them outdated: they finish the submissions they hold and take no new ones, and the row says, for example, code 0.23.0, server 0.24.0: takes no new submissions. So the order is: the server first, then the machines.

# 1. The server, as usual
colloq-host update ghcr.io/colloq-edu/colloq-server:X.Y.Z

# 2. Vast machines: every machine of this server, from a checkout of the repository
make runners-update URL=https://colloq.example.edu

#    or any machine, over SSH, as root
colloq-host runner update

colloq-host runner update learns the server's version from its /api/health, pulls that version's image, drains the machine — the submissions it holds finish, and it takes no new ones — and starts the agent on the new image; colloq-host itself is updated along the way. The drain waits no longer than the longest run the protocol allows (COLLOQ_RUNNER_DRAIN_SEC, 15,720 s by default). With --now it does not wait: the submissions it holds go back to the queue and run again, with no loss and no participant's attempt spent. A version can also be named: colloq-host runner update 0.24.0.

make runners-update does the same on every Vast machine at once. On each machine the update runs in the background and survives a dropped SSH connection, and running the command again follows an update already under way. A machine whose code already matches the server's is left alone (FORCE=1 updates it all the same); NOW=1 is --now; VERSION= is one version for all.

A restart of the server does not cut off the submissions on machines: the machines finish them and send the results once the server is back, and for the first 3 minutes after a start the server counts no machine as gone. Still, update between competitions, and when that is not possible, update the machines right after the server. Machines do not update themselves in this version.

Disconnecting and leaving

  • colloq-host runner leave on the machine: it finishes what it holds, takes no new submissions, revokes itself on the server and removes the agent's container. The cache of images and data stays in /var/lib/colloq-runner; remove the directory to free the disk. Only a new code brings the machine back: it does not join again on the old one, even when a Vast on-start repeats it at boot.
  • make runners-down URL=https://colloq.example.edu does the same for this server's Vast machines, and then their VMs are destroyed with their disks; the command asks first. With NOW=1 the VMs are destroyed at once, without waiting: the server loses the machine after 3 minutes of silence and runs its submissions again, and the machine stays in the list until it is disconnected.
  • Disconnect in the row's menu (or Disconnect all under the list): the server stops accepting the machine's secret at once. Its submissions go back to the queue without spending any quota, late answers are refused, and at its next call the agent purges the hidden test and stops, so that it does not start again. That does not destroy a rented VM, which bills until it is destroyed. Only a new code connects the machine again.

A machine leaving costs participants nothing: the submissions it did not finish run again elsewhere, and the leaving spends neither the daily quota nor attempts.

When a machine fails

  • Silent. A machine the server has not heard for 3 minutes loses its runs: they go back to their place in the queue — ahead of those who came after them — and run again, on another machine or on the server. The participant reads: “The machine running this submission stopped running it. It is back in its place in the queue and will run again; no attempt was spent.” The server counts a machine as gone only when it knows the way to the machines works: another machine answered within the last minute, or its own check of its address passed. When the way itself is gone — the server's tunnel or proxy is down — nothing is lost for up to 15 minutes.
  • Declines. A machine that cannot start a submission — no image, data or packages, not enough disk, memory or card share — gives it back before the container starts. The submission goes to another place at once, and that machine is not offered it for 10 minutes. A decline costs the participant nothing.
  • Loses it again and again. A submission lost by three different machines (or six times on any) is not queued again: it ends as a failure of the server — “This is a failure of the server, not of your notebook; no attempt was spent” — and spends neither the quota nor the ceiling on failed submissions; it can be run again from the console. A submission three different machines declined ends the same way.
  • Hangs. A run that goes past its ceiling — 10 minutes to prepare, the notebook's time, 2 minutes more and 10 minutes to send the result — is taken back by the server and counted as lost, even while the machine keeps answering.
  • Quarantine. Three losses or five declines on one machine within 30 minutes, and the server drains it by itself: it finishes what it holds and takes nothing else, and a banner appears above the list. Look at the events on the machine's page and, once the cause is fixed, press Resume.
  • An agent restart. When the agent's container was restarted or the machine rebooted, the server counts the runs it held as lost at once and queues them again. A stopped agent (docker stop, colloq-host runner update --now) hands them back to the server first, with no loss.

Machines on Vast

From a checkout of the repository, with VAST_TOKEN and an SSH key in .env, as for make vast-vm:

make vast-runner COUNT=3 CODE=<code> URL=https://colloq.example.edu
make vast-runner COUNT=2 GPU="RTX 4090" GPUS=2 DISK=150 CODE=<code> URL=https://colloq.example.edu

The command rents COUNT VMs, 1 to 16, the way make vast-vm does: with the same offer filters (GPU=, GPUS=, GPU_RAM=, CPU=, RAM=, DISK=, MAX_PRICE=) and the same Max CUDA 13.0 floor. It first says what it rents and at what price, and asks to confirm (FORCE=1 does not ask). The machines are rented one after another — each takes the cheapest offer that fits — and boot together; each waits until its agent has joined. The code must allow at least COUNT machines; URL= can be written once into .env as VAST_RUNNER_URL.

The disk is 120 GB by default: Vast has no VMs without cards, and a machine with cards is asked for the GPU kernels. A machine for CPU submissions is a cheaper VM with the cores you need (CPU=), and its card takes GPU submissions as well.

A rented VM's on-start holds only the server's address and the code: no relay token and no other key. The host's operator sees the on-start and Vast keeps it in its console, while the code is worth nothing after a day or after COUNT joins. The machine learns the image version from the server, so a server update needs no new on-start — it needs make runners-update.

The machines are labelled colloq-runner on Vast (colloq-runner-<NAME> with NAME=), and make runners-update and make runners-down find them by that label. They first ask each machine over SSH which server it serves; with URL= only that server's machines are taken, without it every machine of the account with the label.

You pay. The machines bill to your Vast account until they are destroyed. That includes those rented but never joined (the server did not answer, the code ran out of joins): they are in no list of machines. At the end the command names each such machine and prints the command that destroys it, and with DESTROY_UNJOINED=1 it destroys them itself. A machine disconnected in the panel bills too until it is destroyed — with make runners-down or in the Vast console.

Environments from the registry, and GPU kernels

A machine pulls the environment image not from the server but from the registry — by the digest the server recorded when it got that image itself — and before running checks its layers against the server's image. So machines run only the environments whose image the server pulled from a registry. base and kaggle-base are published with every release; the GPU kernels base-gpu and kaggle-gpu by a separate command, make kernel-publish on a machine with a card, at release time (RELEASING.md). The server pulls them from the registry when they are listed in KERNEL_PRELOAD, for example KERNEL_PRELOAD=base,kaggle-base,base-gpu,kaggle-gpu.

An environment built or edited on this server runs on this server only in this version: its image is not in the registry. The list of machines marks such a competition only this server runs it, the editor this server only. With KERNEL_IMAGE_REPO=none the server builds every environment itself, and machines have nothing to run. A GPU kernel the server built itself before its version's kernel was published stays on the server the same way; how to move to the published one is in the same section of RELEASING.md.

What machines do not do yet

  • They do not prepare participants' own packages: the server prepares the sets (on the Docker path it needs Docker Engine 28 or newer), and machines only download the ready ones.
  • They do not run room kernels: classes run on the server, as before.
  • They do not update themselves: after a server update, run make runners-update or colloq-host runner update.
  • They do not sign their requests. A machine presents its secret in a header, and TLS ends at the reverse proxy or relay in front of the server: whoever controls those can read the machines' secrets (see isolation).
  • They do not pick a run up again after an agent restart: such a run runs again.
  • One machine serves one server. Machines are not rented from the panel — only with make vast-runner or by hand.
  • A server in Kubernetes (the Helm chart) does not connect submission machines in this version.
  • There has been no load rehearsal with machines yet: how many submissions a minute a fleet of machines gives, and what that means for a class on the server, has not been measured.
