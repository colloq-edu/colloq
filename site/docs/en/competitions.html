Competitions

A task with a closed evaluation: data, a metric, a leaderboard and a submission queue.

What this is

A competition is a task with a closed evaluation. You hand the class the data and the brief, an entrant submits an .ipynb notebook as a file, the server executes it from scratch and scores the result with your metric. The answers the score is computed against are never shown to an entrant; their place on the leaderboard is.

A competition does not live in a room: it has its own address, /k/<name>, its own queue for the whole instance and its own entrants. No class is needed — a link is enough. You create and run competitions from the admin panel, under Competitions.

This is not an exam system

A submission runs in a throwaway container with no network, and its data is mounted read-only. But a competition does not check who is at the keyboard, and it does not stop two entrants from submitting one solution under two names. If a grade depends on the result, collusion and stand-ins are not something the server will catch for you.

Set a competition up

  1. Open Competitions in the panel and press NEW COMPETITION. Give it a title and an address — the address becomes the /k/<name> link the class opens.
  2. Write the one-line blurb (it shows in the list) and the description in Markdown: the task, what is in the data, what to submit.
  3. Add the open data files. Entrants download them from the task page and see them inside the container as a read-only data/ directory. The ceiling is 200 MB per competition.
  4. Add the hidden answers through their own button. On disk the file is always called solution.csv and it lives outside the class workspaces, so no room can read it. The row key must be named id: it is what the rows are split by and what a submitted file is checked against. No other column name can be set yet, and a competition using one will not open — the baseline check catches it.
  5. If you need one, add a hidden test — input data the notebook reads during the check in place of the open example (see the hidden test). The answers in solution.csv then belong to the hidden test, not to the example.
  6. Paste the metric code, or take a preset (MAPE, RMSE, MAE, ROC AUC, F1, accuracy, QWK) — a preset assembles itself from the columns of your answers file. Say which direction is better: lower or higher.
  7. Upload the sample notebook — the baseline every entrant starts from — and press Run the full check.
  8. Set a deadline and press OPEN COMPETITION.

Until every step is done, the OPEN button stays disabled and names what is missing. The sample notebook is a gate of its own: until it has gone all the way to a number, the competition cannot be opened at all. A task that does not even solve for its author means a hundred people hunting for a mistake of their own that isn't there.

The metric code

A metric is one function. The server calls it with two pandas frames — your answers file and the submitted submission.csv, already joined on the id column. It must return a number.

Before the metric, the platform checks the file itself: it reads as a table, has the id column and no stray index column (Unnamed: 0 from to_csv without index=False), repeats no id, misses none of your answer rows, leaves no prediction empty where your answers have a value, and where your answers hold numbers the predictions are numbers too, without inf — a comma used as the decimal separator is named as such. Ids are compared as the file writes them, as text: when they differ only in case, hyphens or spaces, the entrant sees one of their ids next to the test's. For a key of plain whole numbers, 7.0 and 007 in an answer count as id 7. A submission that fails is refused — the entrant reads what exactly is wrong — and the metric does not run.

import numpy as np
import pandas as pd


class ParticipantVisibleError(Exception):
    pass


def score(solution: pd.DataFrame, submission: pd.DataFrame) -> float:
    if 'orders' not in submission.columns:
        raise ParticipantVisibleError('The submission has no orders column')
    merged = solution.merge(submission, on='id', how='left', suffixes=('_true', '_pred'))
    if merged['orders_pred'].isna().any():
        raise ParticipantVisibleError('Some rows of test.csv have no prediction')
    true = merged['orders_true'].to_numpy(dtype=float)
    pred = merged['orders_pred'].to_numpy(dtype=float)
    return float(np.mean(np.abs((true - pred) / np.maximum(true, 1e-9))))

The text of a ParticipantVisibleError reaches the entrant verbatim — that is how you tell them what is wrong with their file. Any other error is yours alone: the submission is marked metric failed, the entrant reads "the checking code failed", and you get the traceback. After fixing the code press Fix the metric and rescore everyone: notebooks are not re-executed, only the metric runs again.

Check against the baseline runs the metric over the sample notebook's saved answer without executing it again — that turns a code fix into a few seconds of waiting.

The public and the private share

The metric is computed twice: on the public share of the answer rows and on the private one. The public leaderboard is always visible — it is how entrants tell whether they are getting anywhere. The final one stays closed until the deadline: a hidden share you cannot fit to by refreshing the page is the whole point of having one.

The public share is a number in the editor (30 % by default). Rows are split once and for good: the split seed is recorded when the competition is created, so every entrant and every submission faces the same public share. If your answers file has a Usage column holding Public and Private, the split comes from it and the share is not asked for.

What counts is the submission the entrant picked with "Count this one". If they picked none, their best public one counts. The rule can be changed to "best public" or "latest" in the competition's settings. Places are never shared: every leaderboard row has its own, and on equal results the submission sent earlier ranks higher.

The hidden test

An open data/test.csv is downloaded by the class, and an answer is easy to fit to it: count the rows, copy the ids. A hidden test is a file the entrant does not download: at every check the notebook reads it at the same path, in place of the open example. The model is checked on rows nobody has seen.

  1. In the editor's Hidden test section, upload the file through its own button — not through the open data. In Path during the check give its name in data/; by default it is the file's own name. A file named like an open example replaces the example; a file with a new name is added to the data.
  2. The example stays with the entrants: they download it and debug their notebook on it. Check the columns — the editor shows whether they match the example. A notebook written for the example fails on a test with other columns.
  3. The answers in solution.csv must belong to the hidden test's rows.
  4. Run the sample notebook's check again: a change to the hidden test makes its last check stale.

Every run gets a data/ directory of its own: the open files, with the hidden ones in their place. data/test.csv and /data/test.csv both read the hidden test; the metric never sees it. A file replaced in the middle of a run reaches the next runs only. The ceiling is 200 MB and 10 files, apart from the open data.

Entrants see the hidden file's name and row count: the example carries an EXAMPLE mark in the data list, and the check conditions have a line about the hidden test. No link hands out its contents — not to the entrant and not to you: the hidden test cannot be downloaded.

While the notebook runs, the hidden rows are in its memory, and any output can carry them out: test.head(), a KeyError message with a value in it, a metric message quoting the answer. That is why What participants see of a check has two options:

  • Only the outcome and the error type — the default. The entrant sees the outcome, the number of the failed cell and the exception type from a short list of common ones (KeyError, ValueError…). No cell output, no error text, no traceback; the notebook link hands out the notebook as it was sent, not the executed one. A metric refusal is retold in our own words, without values, ids or counts from the answer.
  • Full output — as without a hidden test. Turn it on only if revealing those rows does no harm: fitting the answer to them becomes possible.

In the feed you always see the whole output and the executed notebook. The full text is kept under either option, so a switch applies to every submission at once, with nothing run again.

How a submission is executed

The entrant presses CHOOSE A FILE and sends a notebook. There is no upload straight from a class notebook: a file is the only way in.

  1. The submission joins the instance queue.
  2. In a throwaway container with no network the notebook runs in full, cell by cell, from scratch: no saved variables, and data/ mounted read-only. The notebook must write submission.csv.
  3. That file is taken out of the container and the container is destroyed.
  4. In a second throwaway container — this one with neither the entrant's data nor their code — your metric runs. The hidden answers exist only here.
A submission gets no GPU

A competition's environment is picked from the same list a class uses, but the submission container starts without a GPU, even when an environment with a card is selected. The libraries in the image are the same; the CPU does the work. A task that needs a card cannot be run as a competition yet.

The competition's limits (notebook time, memory, cores) are set in the editor. Time is enforced by killing the container from outside; memory is enforced by Docker. The entrant watches the stages move live and, if the notebook failed, reads their own traceback in full. Each submission has a "Download the notebook with its output" link: the notebook as the server executed it — a failed one too, up to the cell where it stopped. Its output is this run's alone: whatever came from the laptop is cleared before the run.

OutcomeWhat the entrant sees

Notebook failed"Failed on cell 5 of 14" and their traceback verbatim.

That is a competition without a hidden test. With one, an entrant by default sees a failed submission briefly: the outcome, the cell number and the exception type, with no output and no traceback; see the hidden test.

The queue and the console

There is one queue for the whole instance; it lives in the database and survives a server restart. How many submissions run at once is worked out from the machine by default (Auto): its cores and memory, less 2 cores and 2 GB kept for the class, divided by a new submission's default cores and memory. The owner can set a fixed number in the panel's Resources tab; see sizing. The queue is fair per person: someone's second submission queues behind everyone else's first, so no single entrant can hold the runner for the whole session.

The competition console (the Submissions tab) shows what is running now, who is waiting, the five summary numbers and the feed of submissions. A row's menu opens the executed notebook, shows the full output, re-runs it, rescores the metric, or drops it from the standings. The runner strip in the competitions list lets you pause the queue, and a run in progress has a Kill button.

To stop anyone from fitting the public leaderboard with dozens of submissions, set a daily submission quota. Only submissions that get a score spend it. Failed ones — a notebook error, the time or memory limit, a rejected answer, a failure of the metric or of the server itself — and cancelled ones do not; a queued submission holds a place for now and gives it back if it fails. A separate ceiling on failed submissions stops endless failures: at most 10 a day per entrant, or three times the quota if that is more (metric failures do not count toward it). An entrant who reaches it gets a refusal of its own, apart from the quota. With no quota (0) there is no ceiling either.

Entrants and the sign-in key

An entrant is not a room member: their identity belongs to the whole instance. On joining, a person gives their Telegram username or email — the name they appear under on the leaderboard — and receives a sign-in key shaped K7Q-M2X-9FD and a link carrying it. The same key brings them back to their submissions from another device, another browser, or after clearing site data. A username or an address is one person: joining under one the competition already has is refused with a pointer to the sign-in key, and no second identity with another key is created.

The key sits in the "YOUR SIGN-IN KEY" card on the competitions page — shown every time, not once. The key itself is not in the database: what is stored is its fingerprint and a copy encrypted with the instance secret, so a stolen database without that secret opens no one's account.

If an entrant loses their key, issue a new one from the Participants tab. The old one stops working that same second, together with every tab still open on it.

The deadline and the debrief

When the deadline passes, submissions close by themselves and the final leaderboard opens — if the settings say "open it by itself after the deadline". The other option is I will open it by hand — at the review: then a button reveals the results and you choose the minute of the class when they appear.

Finish now closes submissions early.

For those finishing their solution after the bell there is the Late submissions switch in Dates and standings. With it on, submissions keep being accepted after the deadline and after Finish now: they run, get a public score and spend the daily quota by the same rules as ordinary ones. But a late submission never counts: it is in no places, no leaderboard, no summary and not in the wait for the final results, and it cannot be picked to count. The entrant sees its final score when the results open. On their page it is marked “after the deadline · not counted”, and in the console it carries a LATE mark and a Late filter of its own. A submission is late when its upload began after the deadline; one begun on time and finished within two minutes stays in the standings. A late submission never takes the place of an on-time one still waiting for its check.

If you move the deadline later on a running competition, submissions sent before the new deadline become ordinary ones: they join the leaderboard and the standings. Moving it earlier makes no one late. After Finish now moving it changes nothing: the standings were closed by hand.

For the debrief there is Leaderboard on the projector — a separate window with just the table, without file names or internal marks.

Additional packages

The Packages tab shows the pinned Python version and complete base inventory. Entrants can enter additional libraries one per line or import requirements.txt. Comments, on a line of their own or after a requirement (numpy==1.26 # for the metric), and blank lines do not count towards the 32-requirement limit; the whole request is limited to 8 KiB. The server checks compatibility, downloads PyPI wheels and verifies installation without network access. Base package versions cannot be replaced.

Choose a ready set before explicitly confirming notebook submission. Its packages and base image remain bound to that submission; changing the current selection does not alter a rerun. The set is installed into the submission's memory at every run and counts against its limit: it may take at most half, the rest being the kernel's, the data's and the working folder's. A bigger set cannot be chosen, and the entrant sees how much it would take. On the Docker path, preparation requires Docker Engine 28 or newer. Notebook execution and scoring have no internet access.

Checks and reruns

Every attempt has its own identifier and directories. Rescoring an active submission waits for that attempt to finish; an old CSV cannot become the result of a failed new run. Changes to the metric, data, base environment or starter notebook require an up-to-date baseline check. After changing notebook data or its environment, metric-only rescoring is insufficient: rerun the notebook.

Executor availability

Submissions and package preparation run where the rooms' kernels run: on the Docker path (the server image, colloq start) in throwaway containers on the same Docker, on k3s in Pods the broker starts. If the executor or package preparation is unavailable, the interface says why and refuses the work before it enters the queue; /api/health reports each capability separately.
