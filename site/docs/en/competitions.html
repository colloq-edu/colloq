Competitions

A task with a closed evaluation: data, a metric, a leaderboard and a submission queue.

What this is

A competition is a task with a closed evaluation. You hand the class the data and the brief, an entrant submits an .ipynb notebook as a file, the server executes it from scratch and scores the result with your metric. The answers the score is computed against are never shown to an entrant; their place on the leaderboard is.

A competition does not live in a room: it has its own address, /k/<name>, its own queue for the whole instance and its own entrants. No class is needed — a link is enough. You create and run competitions from the admin panel, under Competitions.

This is not an exam system

A submission runs in a throwaway container with no network, and its data is mounted read-only. But a competition does not check who is at the keyboard, and it does not stop two entrants from submitting one solution under two names. If a grade depends on the result, collusion and stand-ins are not something the server will catch for you.

Set a competition up

  1. Open Competitions in the panel and press NEW COMPETITION. Give it a title and an address — the address becomes the /k/<name> link the class opens.
  2. Write the one-line blurb (it shows in the list) and the description in Markdown: the task, what is in the data, what to submit.
  3. Add the open data files. Entrants download them from the task page and see them inside the container as a read-only data/ directory. The ceiling is 200 MB per competition.
  4. Add the hidden answers through their own button. On disk the file is always called solution.csv and it lives outside the class workspaces, so no room can read it. The row key must be named id: it is what the rows are split by and what a submitted file is checked against. No other column name can be set yet, and a competition using one will not open — the baseline check catches it.
  5. If you need one, add a hidden test — input data the notebook reads during the check in place of the open example (see the hidden test). The answers in solution.csv then belong to the hidden test, not to the example.
  6. Paste the metric code, or take a preset (MAPE, RMSE, MAE, ROC AUC, F1, accuracy, QWK) — a preset assembles itself from the columns of your answers file. Say which direction is better: lower or higher.
  7. Upload the sample notebook — the baseline every entrant starts from — and press Run the full check.
  8. Set a deadline and press OPEN COMPETITION.

Until every step is done, the OPEN button stays disabled and names what is missing. The sample notebook is a gate of its own: until it has gone all the way to a number, the competition cannot be opened at all. A task that does not even solve for its author means a hundred people hunting for a mistake of their own that isn't there.

Who sees a competition

An owner sees and runs every competition. A teacher sees the ones they created and the ones in their courses: the Course field in the editor hands a competition to that course's teachers. Anyone else's competition answers “not found” in the panel. The entrants' /k/… page does not change.

After the update to 0.19

Competitions made before the update stay with everyone who was on the staff list at the time, as before. Once a competition is given a course, only that course's teachers, its creator and the owners see it. Teachers added later see only their own competitions and their courses'.

Competition materials

The Materials button in the competition's header in the panel — in the editor of a draft and on the console of an open one — downloads the whole competition as one archive, <address>-materials.zip: a colleague on the course can read the task through or build one like it. Anyone who opens the competition in the editor can download it (see who sees a competition), and each file on its own too: an open file with the download icon in its row, the hidden test and the sample notebook with Download.

In the archiveWhat it is

competition.jsonThe settings and limits: the dates, the environment, the submission's limits, the metric and its direction, the public and private split, the leaderboard and late submission rules, what entrants see of a check, entrants' own packages, and the file list with sizes and rows.

README.mdWhat is in the archive and where the competition's page is.

The answers file, solution.csv, is not in it: it never leaves the server, and no link downloads its contents — competition.json gives only its name, row count and columns. Nothing about entrants is in it either: no entry keys, names, submissions or package sets.

Only the competition's teachers download the hidden test; an entrant never gets it. Every download of it, by its row's link or in the archive, is recorded in the Audit log: who and when, which files and how (“Hidden test downloaded”). Neither the browser nor a proxy keeps these files.

The metric code

A metric is one function. The server calls it with two pandas frames — your answers file and the submitted submission.csv, already joined on the id column. It must return a number.

Before the metric, the platform checks the file itself: it reads as a table, has the id column and no stray index column (Unnamed: 0 from to_csv without index=False), repeats no id, misses none of your answer rows, leaves no prediction empty where your answers have a value, and where your answers hold numbers the predictions are numbers too, without inf — a comma used as the decimal separator is named as such. Ids are compared as the file writes them, as text: when they differ only in case, hyphens or spaces, the entrant sees one of their ids next to the test's. For a key of plain whole numbers, 7.0 and 007 in an answer count as id 7. A submission that fails is refused — the entrant reads what exactly is wrong — and the metric does not run.

import numpy as np
import pandas as pd


class ParticipantVisibleError(Exception):
    pass


def score(solution: pd.DataFrame, submission: pd.DataFrame) -> float:
    if 'orders' not in submission.columns:
        raise ParticipantVisibleError('The submission has no orders column')
    merged = solution.merge(submission, on='id', how='left', suffixes=('_true', '_pred'))
    if merged['orders_pred'].isna().any():
        raise ParticipantVisibleError('Some rows of test.csv have no prediction')
    true = merged['orders_true'].to_numpy(dtype=float)
    pred = merged['orders_pred'].to_numpy(dtype=float)
    return float(np.mean(np.abs((true - pred) / np.maximum(true, 1e-9))))

The text of a ParticipantVisibleError reaches the entrant verbatim — that is how you tell them what is wrong with their file. Any other error is yours alone: the submission is marked metric failed, the entrant reads "the checking code failed", and you get the traceback. After fixing the code press Fix the metric and rescore everyone: notebooks are not re-executed, only the metric runs again.

Check against the baseline runs the metric over the sample notebook's saved answer without executing it again — that turns a code fix into a few seconds of waiting.

The public and the private share

The metric is computed twice: on the public share of the answer rows and on the private one. The public leaderboard is always visible — it is how entrants tell whether they are getting anywhere. The final one stays closed until the deadline: a hidden share you cannot fit to by refreshing the page is the whole point of having one.

The public share is a number in the editor (30 % by default). Rows are split once and for good: the split seed is recorded when the competition is created, so every entrant and every submission faces the same public share. If your answers file has a Usage column holding Public and Private, the split comes from it and the share is not asked for.

What counts is the submission the entrant picked with "Count this one". If they picked none, their best public one counts. The rule can be changed to "best public" or "latest" in the competition's settings. Places are never shared: every leaderboard row has its own, and on equal results the submission sent earlier ranks higher.

The hidden test

An open data/test.csv is downloaded by the class, and an answer is easy to fit to it: count the rows, copy the ids. A hidden test is a file the entrant does not download: at every check the notebook reads it at the same path, in place of the open example. The model is checked on rows nobody has seen.

  1. In the editor's Hidden test section, upload the file through its own button — not through the open data. In Path during the check give its name in data/; by default it is the file's own name. A file named like an open example replaces the example; a file with a new name is added to the data.
  2. The example stays with the entrants: they download it and debug their notebook on it. Check the columns — the editor shows whether they match the example. A notebook written for the example fails on a test with other columns.
  3. The answers in solution.csv must belong to the hidden test's rows.
  4. Run the sample notebook's check again: a change to the hidden test makes its last check stale.

Every run gets a data/ directory of its own: the open files, with the hidden ones in their place. data/test.csv and /data/test.csv both read the hidden test; the metric never sees it. A file replaced in the middle of a run reaches the next runs only. The ceiling is 200 MB and 10 files, apart from the open data.

Entrants see the hidden file's name and row count: the example carries an EXAMPLE mark in the data list, and the check conditions have a line about the hidden test. No link hands its contents to an entrant. You and the competition's other teachers download the file with Download in its row or in the materials archive, and every such download is recorded in the audit log.

While the notebook runs, the hidden rows are in its memory, and any output can carry them out: test.head(), a KeyError message with a value in it, a metric message quoting the answer. That is why What participants see of a check has two options:

  • Only the outcome and the error type — the default. The entrant sees the outcome, the number of the failed cell and the exception type from a short list of common ones (KeyError, ValueError…). No cell output, no error text, no traceback; the notebook link hands out the notebook as it was sent, not the executed one. A metric refusal is retold in our own words, without values, ids or counts from the answer.
  • Full output — as without a hidden test. Turn it on only if revealing those rows does no harm: fitting the answer to them becomes possible.

In the feed you always see the whole output and the executed notebook. The full text is kept under either option, so a switch applies to every submission at once, with nothing run again.

How a submission is executed

The entrant presses CHOOSE A FILE and sends a notebook. There is no upload straight from a class notebook: a file is the only way in.

Entrants download the open files one by one, or with Download all above the list: the archive holds data/ with every file and the starter notebooks next to it, as in the check, so pd.read_csv('data/train.csv') works right after unpacking. Hidden answers and the hidden test are never in it.

  1. The submission joins the instance queue.
  2. In a throwaway container with no network the notebook runs in full, cell by cell, from scratch: no saved variables, and data/ mounted read-only. The notebook must write submission.csv.
  3. That file is taken out of the container and the container is destroyed.
  4. In a second throwaway container — this one with neither the entrant's data nor their code — your metric runs. The hidden answers exist only here.

Steps 2 and 3 may run not on this server but on a submission machine connected to it — in the same sandbox, with the same limits. Step 4, the metric, always runs on the server, and the hidden answers never leave it.

A card only when the competition asks for one

A competition's environment is picked from the same list a class uses. On an environment with CUDA, such as base-gpu or kaggle-gpu, the libraries are the same as in class, but a submission gets a card only when the competition's GPU switch is on and the owner has given this server's cards to submissions or connected a submission machine with cards. With the switch off the CPU does the work; with it on and no card given, the competition refuses uploads and the baseline check. See a card for submissions.

The competition's limits (notebook time, memory, cores, and the GPU switch) are set in the editor. Time is enforced by killing the container from outside; memory is enforced by Docker. The entrant watches the stages move live and, if the notebook failed, reads their own traceback in full. Each submission has a "Download the notebook with its output" link: the notebook as the server executed it — a failed one too, up to the cell where it stopped. Its output is this run's alone: whatever came from the laptop is cleared before the run.

OutcomeWhat the entrant sees
DoneThe public score and their place.
Notebook failed"Failed on cell 5 of 14" and their traceback verbatim.
Time limit"Did not fit into 10 minutes, cell 6 of 50".
Out of memory"Took more than 4 GB, cell 2".
Answer not accepted"Reached the end but left no submission.csv", "The answer is missing 3 rows, for example id=17" — or the text of your ParticipantVisibleError.
Metric failed"The checking code failed", with no detail; you get the traceback and the submission waits to be rescored.

That is a competition without a hidden test. With one, an entrant by default sees a failed submission briefly: the outcome, the cell number and the exception type, with no output and no traceback; see the hidden test.

A submission can be given up to 32 cores — more than this server has, too. The server leaves such a notebook to a submission machine with enough cores. If no such machine is online, or it will not take this submission (it declined it, or offers no places), the server runs the notebook itself — if it runs this competition's notebooks at all — on all its own cores, and the run's All output says how many cores it ran on instead of how many; the entrant is not told. The metric always runs on the server, on its cores. Memory is never cut this way: a notebook that needs more memory than the server can give a submission is one it never runs — it waits for a machine with enough memory while the queue moves past it, and until there is one the entrant sees “getting ready”. Under the cores and memory fields the editor says what will happen to such submissions. In a Kubernetes install the submission's Pod gets exactly the cores and memory set, and placing it is the cluster's job.

A card for submissions

A notebook that trains a network wants a video card. A submission gets a share of one when two things are true: the server owner has given cards to submissions, and the competition asks for one.

  1. The owner gives cards. In the panel's Resources tab, the GPUs for submissions block lists the machine's cards (KERNEL_GPUS) with their names and memory. Tick the ones that serve submissions and say how many submissions share one card at a time, from 1 to 8. A card given to submissions leaves the rooms' pool, so a class and a submission never share a card; a class that holds the card at that moment keeps it until its container ends, and submissions wait for it until then; the other way round, a card given back to the rooms serves a class once the submissions running on it end. On a machine set up without the panel, COMPETITION_GPUS (entries of KERNEL_GPUS, comma-separated) and COMPETITION_GPU_PER_DEVICE do the same; what the panel saved wins.
  2. The competition asks. In the editor, pick an environment with CUDA (base-gpu, kaggle-gpu or one of your own on top of them) and turn the GPU switch on. Only such environments have it, and while it is on the environment cannot be changed to one without CUDA. Only the notebook gets the card. The metric never does: it holds the hidden answers and has nothing to train. The metric of such a competition runs in the light kaggle-base image (numpy, pandas, scikit-learn, scipy), pinned to the competition, not in its GPU image: a metric that imports torch fails as metric code (see the metric of a competition with a GPU).

The share. Submissions on one card get equal parts of its memory: on a 24 GB card with 3 at a time, 8 GB each. With cards of different sizes, the share promised is the smallest card's: it holds on whichever card a run lands. The number per card may change during a class: a running submission keeps the share it started with, and a card takes a new one only once its share fits beside theirs, so a card raised from 1 to 2 while a submission has it whole takes nobody else until that one ends.

How the share is held. From two sides. Inside the submission, PyTorch is capped at the share less 512 MB for the CUDA context, also when a library such as polars looks for it before the notebook imports it: a model that outgrows the cap fails in its cell with torch.OutOfMemoryError, as it would on a smaller card. CatBoost on the GPU takes 95 % of the card's free memory at once by default; within a share its gpu_ram_part becomes the share's part of the card less the CUDA context (about 0.48 with 2 to a 24 GB card), unless the notebook sets its own. XGBoost on device="cuda" takes memory as it goes, not up front. TensorFlow and JAX, in an environment of your own, are not capped: by default both take most of the card at once, and the runner stops them for it, unless the notebook holds them back before importing them (TF_FORCE_GPU_ALLOW_GROWTH=true, XLA_PYTHON_CLIENT_PREALLOCATE=false). From outside, every 3 seconds the runner reads how much of the card the submission's container really holds, PyTorch or not, and stops a submission that is more than 256 MB over its share twice in a row. It reads as root, which the notebook's own code cannot signal, and it fails closed: a submission whose card cannot be read 4 times in a row (about 12 seconds) is stopped too, because a run nobody watches may be holding the whole card. With 1 submission per card, the whole card is the submission's, and nothing is capped or watched. A card that cannot tell its memory has no share to promise: the panel says its size is unknown, and nothing is capped or watched either.

What the entrant sees. The competition page shows the share of the card next to the other limits. A notebook that hit the cap inside ends as Notebook failed with that torch.OutOfMemoryError and a line of ours naming its share; a submission stopped from outside ends as Out of memory, naming its share and how much it took. With a hidden test, under the default Only the outcome and the error type, the message names only the share: how far past it a run went is a number its notebook chose (see the hidden test). A submission whose card stopped answering is stopped as Notebook failed and counts as a failed one: that happens when a notebook keeps its processor busy with hundreds of threads or processes, or when the card itself stops answering. If the card never answered during the run, the host is to blame, not the notebook: the submission ends as the server's own failure, which counts toward nothing, and the teacher's log says to check nvidia-smi inside a container. A burst outside the cap can take a neighbour's memory in the seconds before the runner's second reading: a submission that runs out of video memory (torch.OutOfMemoryError) while the runner is stopping another one on the same card for going past its share goes back to the queue once, with a line saying so, and that attempt does not count. If none of this server's cards is given to submissions and no submission machine with cards was heard within the last hour, a competition with GPU on refuses uploads and the baseline check outright and says why: nothing waits in the queue for a card that will not come.

What a share does not give. A card does not speed a notebook up by itself: only what the notebook has moved to CUDA runs on it, its model and tensors (model.to("cuda"), batch.to("cuda")). A notebook written for the CPU runs on the CPU with a share of a card too, on the submission's cores. Submissions on one card take turns at its compute: three at a time, a model that keeps the card busy trains about three times slower than alone, and the notebook time limit counts that time. The share protects memory, not speed: raise the time limit, or put fewer submissions on a card. A small model leaves the card idle between its steps and hardly notices its neighbours; see the measurement below. In the queue a GPU submission needs a free runner and a free share of a card; while it waits for the card, CPU submissions behind it go ahead.

What a card gives a class. Measured on 13 October 2026 on a Vast VM with 61 vCPU, 98 GB of memory and 2 × RTX 4090 (24 GB each): 25 entrants sent the reference solution of a letter-recognition competition — a small convolutional network; 2 cores, 4 GB and 600 seconds per submission; kaggle-gpu — at the same moment, and every submission scored. A run is the time a submission spent running; a verdict counts from its upload.

Cards for submissionsRun, medianVerdict, medianVerdict, last

1 card × 425 s102 s175 s

A card makes one run of this notebook five to six times shorter, and after that the class waits for the queue, not for the run: eight to a card ran nearly as fast as four, and two cards with eight each gave all 25 their verdict in about a minute. A bigger model gains less from more submissions to a card, and must fit into the smaller share. A mixed load of 10 GPU and 4 CPU submissions on the same machine kept the queue's rule: the CPU ones did not wait behind the GPU ones.

On Kubernetes the cluster decides what a share is: the chart value gpu.competitions.resource names the device-plugin resource a GPU submission requests, a whole card, a time-sliced replica or a MIG slice; see operations. How many GPU submissions go to the cluster at once is gpu.competitions.slots, one while it is unset: the queue keeps that many there and lets CPU submissions go past the rest, as past a full card here. Colloq caps and watches nothing there itself: a MIG slice has memory of its own, while time-sliced replicas share the card's memory with no limit between them. Nor does a card leave the rooms there: GPU rooms request nvidia.com/gpu, so with that name submissions take their units from the rooms' cards, and a GPU room that finds none free is refused while submissions hold them. Where classes use GPU rooms, give submissions a resource of their own; see GPU nodes.

Cards of submission machines. GPU submissions are also taken by connected submission machines with cards. A machine gives all its cards to submissions and sets the share itself — its card's memory divided by the runs per card (its own setting or, by default, this server's Runs per card) — and the same runner described above holds it. While a machine with cards was heard within the last hour, a competition with GPU on takes uploads even on a server with no cards of its own: they wait in the queue for the machine instead of being refused. The server needs such a competition's GPU image only to pin the environment to the competition and to prepare participants' own packages: it takes uploads and scores their metric without it, in kaggle-base, as long as the competition's metric runs there, its environment came from a registry and a machine with cards that fits one of its submissions was heard within the last hour (see what machines need).

The queue and the console

There is one queue for the whole instance; it lives in the database and survives a server restart. How many submissions run at once is worked out from the machine by default (Auto): its cores and memory, less 2 cores and 2 GB kept for the class, divided by a new submission's default cores and memory. The owner can set a fixed number in the panel's Resources tab; see sizing. The queue is fair per person: someone's second submission queues behind everyone else's first, so no single entrant can hold the runner for the whole session.

Connected submission machines take work from the same queue in the same order: their places add to the server's. While no place can take a submission yet — the machines are still downloading its environment image or data, or no machine that fits is online — the entrant sees “getting ready” instead of a place in the queue, and “being scored” once the notebook has run and waits for its metric on the server. A submission a machine did not finish goes back to its place in the queue; that loss spends neither the quota nor the entrant's attempts.

The competition console (the Submissions tab) shows what is running now, who is waiting, the five summary numbers and the feed of submissions. A row's menu opens the executed notebook, shows the full output, re-runs it, rescores the metric, or drops it from the standings. The runner strip in the competitions list lets you pause the queue, and a run in progress has a Kill button. An owner deletes a competition with Delete competition in its row's menu in the list, and its runs go first: the waiting submissions leave the queue, and the running ones are killed and waited for, up to 30 seconds each. If one has not stopped by then, nothing is deleted, though the waiting ones stay cancelled, and the delete can be repeated a minute later.

To stop anyone from fitting the public leaderboard with dozens of submissions, set a daily submission quota. Only submissions that get a score spend it. Failed ones — a notebook error, the time or memory limit, a rejected answer, a failure of the metric or of the server itself — and cancelled ones do not; a queued submission holds a place for now and gives it back if it fails. A separate ceiling on failed submissions stops endless failures: at most 10 a day per entrant, or three times the quota if that is more (metric failures do not count toward it). An entrant who reaches it gets a refusal of its own, apart from the quota. With no quota (0) there is no ceiling either.

Entrants and the sign-in key

An entrant is not a room member: their identity belongs to the whole instance. On joining, a person gives their Telegram username or email — the name they appear under on the leaderboard — and receives a sign-in key shaped K7Q-M2X-9FD and a link carrying it. The same key brings them back to their submissions from another device, another browser, or after clearing site data. A username or an address is one person: joining under one the competition already has is refused with a pointer to the sign-in key, and no second identity with another key is created.

The key sits in the "YOUR SIGN-IN KEY" card on the competitions page — shown every time, not once. The key itself is not in the database: what is stored is its fingerprint and a copy encrypted with the instance secret, so a stolen database without that secret opens no one's account.

If an entrant loses their key, issue a new one from the Participants tab. The old one stops working that same second, together with every tab still open on it.

The deadline and the debrief

When the deadline passes, submissions close by themselves and the final leaderboard opens — if the settings say "open it by itself after the deadline". The other option is I will open it by hand — at the review: then a button reveals the results and you choose the minute of the class when they appear.

Finish now closes submissions early. After the deadline there is no need to press it: the competition counts as finished anyway — participants and the panel list it among the finished ones, and the console header offers Close late intake or Take late submissions instead of Finish now, plus Open the private leaderboard when the results open by hand.

For those finishing their solution after the bell there is the Late submissions switch in Dates and standings. With it on, submissions keep being accepted after the deadline and after Finish now: they run, get a public score and spend the daily quota by the same rules as ordinary ones. But a late submission never counts: it is in no places, no leaderboard, no summary and not in the wait for the final results, and it cannot be picked to count. The entrant sees its final score when the results open. On their page it is marked “after the deadline · not counted”, and in the console it carries a LATE mark and a Late filter of its own. A submission is late when its upload began after the deadline; one begun on time and finished within two minutes stays in the standings. A late submission never takes the place of an on-time one still waiting for its check. While late intake is open, the lists say so: participants see the competition among the finished ones marked “late submissions open”, with a button, and the panel writes “late ones accepted” under FINISHED, with how many came.

If you move the deadline later on a running competition, submissions sent before the new deadline become ordinary ones: they join the leaderboard and the standings. Moving it earlier makes no one late. After Finish now moving it changes nothing: the standings were closed by hand.

For the debrief there is Leaderboard on the projector — a separate window with just the table, without file names or internal marks.

Additional packages

The Packages tab shows the pinned Python version and complete base inventory. Entrants can enter additional libraries one per line or import requirements.txt. Comments, on a line of their own or after a requirement (numpy==1.26 # for the metric), and blank lines do not count towards the 32-requirement limit; the whole request is limited to 8 KiB. The server checks compatibility, downloads PyPI wheels and verifies installation without network access. Base package versions cannot be replaced.

Choose a ready set before explicitly confirming notebook submission. Its packages and base image remain bound to that submission; changing the current selection does not alter a rerun. The set is installed into the submission's memory at every run and counts against its limit: it may take at most half, the rest being the kernel's, the data's and the working folder's. A bigger set cannot be chosen, and the entrant sees how much it would take. On the Docker path, preparation requires Docker Engine 28 or newer. Notebook execution and scoring have no internet access.

Checks and reruns

Every attempt has its own identifier and directories. Rescoring an active submission waits for that attempt to finish; an old CSV cannot become the result of a failed new run. Changes to the metric, data, base environment or starter notebook require an up-to-date baseline check. After changing notebook data or its environment, metric-only rescoring is insufficient: rerun the notebook.

Executor availability

Submissions and package preparation run where the rooms' kernels run: on the Docker path (the server image, colloq start) in throwaway containers on the same Docker, on k3s in Pods the broker starts. Connected submission machines can run submission notebooks too; the metric and package preparation always run on the server. If the executor or package preparation is unavailable, the interface says why and refuses the work before it enters the queue; /api/health reports each capability separately. A competition with GPU on also needs a share of a card: with no card given to submissions (on Kubernetes, no GPU resource set for them), and on the Docker path no submission machine with cards heard within the last hour either, it refuses uploads and the baseline check with that reason.
