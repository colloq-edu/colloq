Соревнования

Задача с закрытой проверкой: данные, метрика, лидерборд и очередь посылок.

Что это такое

Соревнование — это задача с закрытой проверкой. Вы даёте классу данные и условие, участник присылает тетрадь .ipynb файлом, сервер исполняет её с нуля и считает результат вашей метрикой. Ответы, по которым считается результат, участник не видит никогда, а в лидерборде видит своё место.

Соревнование живёт не в комнате: у него свой адрес вида /k/<имя>, своя очередь на весь инстанс и свои участники. Занятие для него не нужно — достаточно ссылки. Заводят и ведут соревнование в панели, в разделе «Соревнования».

Это не экзаменационная система

Посылка исполняется в одноразовом контейнере без сети, и данные в нём только на чтение. Но соревнование не проверяет, кто именно сидит за клавиатурой, и не мешает двум участникам прислать одно решение под разными именами. Если по результату ставится оценка, сговор и подмену автора придётся ловить не сервером.

Заведите соревнование

  1. В панели откройте «Соревнования» и нажмите «НОВОЕ СОРЕВНОВАНИЕ». Дайте название и адрес — адрес попадёт в ссылку /k/<имя>, и по ней класс откроет задачу.
  2. Напишите краткую строку (её видно в списке) и описание в Markdown: условие, что лежит в данных и что сдавать.
  3. Положите открытые файлы данных. Участник скачивает их со страницы задачи и видит внутри контейнера как каталог data/, только на чтение. Потолок — 200 МБ на соревнование.
  4. Положите скрытые ответы отдельной кнопкой. На диске файл всегда называется solution.csv и лежит вне рабочих папок занятий, поэтому из комнаты его не прочитать. Ключ строки обязан называться id: по нему делятся строки и сверяется присланный файл. Другого имени колонки пока не задать, и соревнование с ним не откроется — проверка бейзлайна это поймает.
  5. Если нужно, положите скрытый тест — входные данные, которые тетрадь читает при проверке вместо открытого примера (см. скрытый тест). Тогда ответы в solution.csv — к скрытому тесту, а не к примеру.
  6. Вставьте код метрики или возьмите заготовку (MAPE, RMSE, MAE, ROC AUC, F1, accuracy, QWK) — заготовка соберётся по колонкам вашего файла ответов. Укажите, в какую сторону лучше: меньше или больше.
  7. Загрузите сэмпл-тетрадь — базовое решение, с которого начинает каждый участник, — и нажмите «Проверить целиком».
  8. Поставьте дедлайн и нажмите «ОТКРЫТЬ СОРЕВНОВАНИЕ».

Пока какой-нибудь из шагов не сделан, кнопка «ОТКРЫТЬ СОРЕВНОВАНИЕ» не нажимается и называет недостающее. Отдельный гейт — сэмпл-тетрадь: пока она не прошла весь путь до числа, соревнование не открыть вовсе. Задача, которая не решается даже у автора, — это сто человек, безуспешно ищущих ошибку у себя.

Кто видит соревнование

Владелец видит и ведёт все соревнования. Преподаватель — те, что создал сам, и соревнования своих курсов: поле «Курс» в редакторе отдаёт соревнование преподавателям выбранного курса. Чужие соревнования в панели отвечают «не найдено». Страница /k/… для участников от этого не меняется.

После обновления до 0.19

Соревнования, заведённые до обновления, остаются у всех, кто тогда уже был в списке преподавателей, — как было раньше. Как только соревнованию выбирают курс, его видят только преподаватели этого курса, автор и владелец. Новые преподаватели видят только свои соревнования и соревнования своих курсов.

Код метрики

Метрика — одна функция. Сервер зовёт её с двумя таблицами pandas: вашим файлом ответов и присланным submission.csv, уже сведёнными по колонке id. Вернуть надо число.

До метрики файл проверяет сама платформа: он читается как таблица, в нём есть колонка id и нет лишней колонки индекса (Unnamed: 0 от to_csv без index=False), ни один id не повторяется, ни одна строка ваших ответов не пропущена, нет пустых прогнозов там, где в ответах есть значение, а там, где в ответах числа, прогнозы тоже числа и без inf — запятую вместо десятичной точки платформа называет прямо. id сравниваются так, как записаны в файле, строкой: если они отличаются только регистром, дефисами или пробелами, участник видит пример своего id рядом с тестовым. Для ключа из обычных целых чисел 7.0 и 007 в ответе считаются тем же id 7. Посылку, которая не прошла проверку, платформа отклоняет — участник видит, что именно не так, — и метрика не запускается.

import numpy as np
import pandas as pd


class ParticipantVisibleError(Exception):
    pass


def score(solution: pd.DataFrame, submission: pd.DataFrame) -> float:
    if 'orders' not in submission.columns:
        raise ParticipantVisibleError('В ответе нет колонки orders')
    merged = solution.merge(submission, on='id', how='left', suffixes=('_true', '_pred'))
    if merged['orders_pred'].isna().any():
        raise ParticipantVisibleError('Не для всех строк test.csv есть прогноз')
    true = merged['orders_true'].to_numpy(dtype=float)
    pred = merged['orders_pred'].to_numpy(dtype=float)
    return float(np.mean(np.abs((true - pred) / np.maximum(true, 1e-9))))

Текст ParticipantVisibleError участник читает дословно — это и есть способ объяснить ему, чем плох его файл. Любая другая ошибка видна только вам: посылка помечается «УПАЛА МЕТРИКА», участник видит фразу «проверяющий код упал», а трассировку — вы. Поправив код, нажмите «Исправить метрику и пересчитать всех»: тетради при этом не перезапускаются, считается только метрика.

«Проверить на бейзлайне» прогоняет метрику по сохранённому ответу сэмпл-тетради, не запуская её заново, — так правку кода проверяют за секунды.

Публичная и приватная части

Метрика считается дважды: на публичной части строк ответа и на приватной. Публичный лидерборд виден всегда — по нему участники понимают, движутся ли они. Итоговый закрыт до дедлайна: под скрытую часть нельзя подогнаться, обновляя страницу.

Доля публичной части задаётся числом в редакторе (по умолчанию 30 %). Строки делятся один раз и навсегда: зерно деления записывается при заведении соревнования, поэтому у всех участников и у всех посылок публичная часть одна и та же. Если в файле ответов есть колонка Usage со значениями Public и Private, деление берётся из неё, а доля не спрашивается.

В зачёт идёт та посылка, которую участник выбрал сам кнопкой «Выбрать в зачёт». Не выбрал — лучшая по публичной части. Правило зачёта можно сменить на «лучшая по публичной» или «последняя» в настройках соревнования. Общих мест нет: у каждой строки лидерборда своё, и при одинаковом результате выше посылка, отправленная раньше.

Скрытый тест

Открытый data/test.csv класс скачивает, и по нему легко подогнать ответ: посчитать строки, выписать id. Скрытый тест — файл, который участник не скачивает: на каждой проверке тетрадь читает его по тому же пути, вместо открытого примера. Модель проверяется на строках, которых никто не видел.

  1. В редакторе, в разделе «Скрытый тест», загрузите файл своей кнопкой — не через открытые данные. В поле «Путь при проверке» укажите имя в data/: по умолчанию это имя самого файла. Файл с именем открытого примера подменяет пример, файл с новым именем добавляется к данным.
  2. Пример остаётся у участников: его скачивают и на нём отлаживают тетрадь. Сверьте колонки — редактор показывает, совпадают ли они с примером. Тетрадь, написанная под пример, упадёт на тесте с другими колонками.
  3. Ответы в solution.csv должны быть к строкам скрытого теста.
  4. Проверьте сэмпл-тетрадь заново: смена скрытого теста делает её прошлую проверку устаревшей.

Каждый прогон получает собственный каталог data/: открытые файлы и скрытые на их месте. data/test.csv и /data/test.csv читают скрытый тест, метрика его не видит вовсе. Файл, заменённый посреди прогона, достаётся только следующим прогонам. Потолок — 200 МБ и 10 файлов, отдельно от открытых данных.

Участник видит имя скрытого файла и число строк: в списке данных у примера стоит отметка «ПРИМЕР», а в условиях проверки — строка о скрытом тесте. Содержимого не отдаёт ни одна ссылка, ни участнику, ни вам: скачать скрытый тест нельзя.

Пока тетрадь работает, скрытые строки у неё в памяти, и любой вывод может их вынести: test.head(), текст KeyError со значением, сообщение метрики, которое цитирует ответ. Поэтому в разделе «Что показывать участнику при проверке» два варианта:

  • «Только статус и тип ошибки» — по умолчанию. Участник видит исход, номер упавшей ячейки и тип исключения из короткого списка обычных (KeyError, ValueError…). Ни вывода ячеек, ни текста ошибки, ни трассировки; ссылка на тетрадь отдаёт тетрадь в том виде, в каком её прислали, а не исполненную. Отказ метрики пересказывается нашими словами, без значений, id и чисел из ответа.
  • «Полный вывод» — как без скрытого теста. Включайте, только если раскрыть эти строки не страшно: подогнать ответ по ним станет можно.

Вы в ленте всегда видите весь вывод и исполненную тетрадь. Полный текст хранится при любом варианте, поэтому переключение действует сразу на все посылки, без повторного исполнения.

Как исполняется посылка

Участник нажимает «ВЫБРАТЬ ФАЙЛ» и отправляет тетрадь. Загрузки прямо из тетради занятия нет: только файл.

Открытые файлы участник скачивает по одному или кнопкой «Скачать всё» над списком: в архиве папка data/ со всеми файлами и стартовые тетради рядом с ней, как при проверке, поэтому pd.read_csv('data/train.csv') работает сразу после распаковки. Скрытых ответов и скрытого теста в архиве нет.

  1. Посылка встаёт в очередь инстанса.
  2. В одноразовом контейнере без сети тетрадь исполняется целиком, ячейка за ячейкой, с нуля: сохранённых переменных нет, каталог data/ примонтирован только на чтение. Тетрадь обязана записать submission.csv.
  3. Файл забирается из контейнера, контейнер сносится.
  4. Во втором одноразовом контейнере — уже без данных участника и без его кода — запускается ваша метрика. Скрытые ответы бывают только здесь.
Карта — только когда соревнование её просит

Окружение соревнования выбирают из того же списка, что и для занятия. На окружении с CUDA, например base-gpu или kaggle-gpu, библиотеки те же, что на занятии, но карту посылка получает, только если в соревновании включён переключатель «Видеокарта», а владелец отдал посылкам карты. С выключенным переключателем считает процессор; с включённым, пока карт нет, соревнование отказывает в загрузке и в проверке бейслайна. См. видеокарту для посылок.

Пределы соревнования (время на тетрадь, память, ядра и переключатель «Видеокарта») стоят в редакторе. По времени контейнер убивают снаружи, по памяти его ограничивает docker. Участник видит движение этапов вживую и, если тетрадь упала, свою трассировку целиком. У посылки есть ссылка «Скачать тетрадь с выводом»: это тетрадь в том виде, в каком её исполнил сервер, — у упавшей тоже, до ячейки, на которой она остановилась. Вывод в ней только этого прогона: присланный с ноутбука стирается перед запуском.

ИсходЧто видит участник
ГОТОВОПубличный результат и своё место.
УПАЛА ТЕТРАДЬ«Упала на ячейке 5 из 14» и свою трассировку дословно.
ЛИМИТ ВРЕМЕНИ«Не уложилась в 10 минут, ячейка 6 из 50».
НЕ ХВАТИЛО ПАМЯТИ«Заняла больше 4 ГБ, ячейка 2».
ОТВЕТ НЕ ПРИНЯТ«Дошла до конца, но submission.csv не оставила», «В ответе нет 3 строк, например id=17» — или текст вашего ParticipantVisibleError.
УПАЛА МЕТРИКА«Проверяющий код упал» без подробностей; трассировку видите вы, и посылка ждёт пересчёта.

Так выглядит соревнование без скрытого теста. Со скрытым тестом участник по умолчанию видит упавшую посылку коротко: исход, номер ячейки и тип исключения, без вывода и трассировки, см. скрытый тест.

Видеокарта для посылок

Тетради, которая учит нейросеть, нужна видеокарта. Посылка получает долю карты, когда сошлись два условия: владелец сервера отдал посылкам карты, и соревнование карту просит.

  1. Владелец отдаёт карты. Во вкладке «Ресурсы» панели блок «Видеокарты для посылок» перечисляет карты машины (KERNEL_GPUS) с названиями и памятью. Отметьте те, что служат посылкам, и задайте, сколько посылок делят одну карту одновременно, от 1 до 8. Отданная посылкам карта уходит из пула комнат, поэтому занятие и посылка никогда не делят одну карту; занятие, которое держит карту в этот момент, сохраняет её, пока работает его контейнер, а посылки до тех пор её ждут; и наоборот, карта, возвращённая комнатам, начинает служить занятию, когда закончатся идущие на ней посылки. На машине, настроенной без панели, то же задают COMPETITION_GPUS (элементы KERNEL_GPUS через запятую) и COMPETITION_GPU_PER_DEVICE; сохранённое в панели главнее.
  2. Соревнование просит карту. В редакторе выберите окружение с CUDA (base-gpu, kaggle-gpu или своё поверх них) и включите переключатель «Видеокарта». Он есть только у таких окружений, и пока он включён, окружение нельзя сменить на окружение без CUDA. Карту получает только тетрадь. Метрика не получает никогда: у неё скрытые ответы, и учить ей нечего.

Доля карты. Посылки на одной карте получают поровну её памяти: на карте 24 ГБ при трёх одновременно — по 8 ГБ. Если карты разного размера, обещанная доля — по наименьшей из них: её хватит на любой карте. Число посылок на карту можно менять и посреди занятия: идущая посылка сохраняет долю, с которой началась, а новую карта берёт, только когда её доля помещается рядом с их долями, — поэтому карта, которую одна посылка занимает целиком, после перехода с 1 на 2 никого больше не возьмёт, пока та не закончится.

Как держат долю. С двух сторон. Внутри посылки PyTorch ограничен долей за вычетом 512 МБ на контекст CUDA, даже если какая-нибудь библиотека, например polars, ищет его раньше, чем тетрадь его импортирует: модель, которая выросла из ограничения, падает в своей ячейке с torch.OutOfMemoryError, как на карте поменьше. CatBoost на GPU по умолчанию сразу берёт 95 % свободной памяти карты; в доле его gpu_ram_part — та часть карты, которую составляет доля за вычетом контекста CUDA (около 0,48 при двух посылках на карте 24 ГБ), если тетрадь не задала свою. XGBoost на device="cuda" берёт память по ходу дела, а не заранее. TensorFlow и JAX в своём окружении не ограничиваются: по умолчанию оба сразу занимают большую часть карты, и исполнитель останавливает их за это, если тетрадь не придержит их до импорта (TF_FORCE_GPU_ALLOW_GROWTH=true, XLA_PYTHON_CLIENT_PREALLOCATE=false). Снаружи исполнитель каждые 3 секунды смотрит, сколько памяти карты на самом деле держит контейнер посылки, PyTorch это или нет, и останавливает посылку, которая дважды подряд превысила долю больше чем на 256 МБ. Смотрит он от root, которому код тетради не может послать сигнал. А посылку, карту которой 4 раза подряд не удалось прочитать (около 12 секунд), тоже останавливают: прогон, за которым никто не смотрит, может держать всю карту. Если на карте одна посылка, карта целиком её, и ничего не ограничивается и не проверяется. Если карта не сообщила свой объём, обещать нечего: панель пишет, что размер неизвестен, и ничего не ограничивается и не проверяется тоже.

Что видит участник. На странице соревнования доля карты стоит рядом с остальными пределами. Тетрадь, упёршаяся в ограничение изнутри, — это «Упала тетрадь» с тем самым torch.OutOfMemoryError и нашей строкой о её доле; посылка, остановленная снаружи, — «Не хватило памяти» с её долей и тем, сколько она заняла. Со скрытым тестом при варианте «Только статус и тип ошибки», который стоит по умолчанию, в сообщении только доля: сколько заняла посылка — число, которое выбрала её тетрадь (см. скрытый тест). Посылка, карта которой перестала отвечать, останавливается как «Упала тетрадь» и считается упавшей: так бывает, когда тетрадь занимает процессор сотнями потоков или процессов или когда сама карта перестаёт отвечать. Если же карта не ответила за весь прогон ни разу, виноват хост, а не тетрадь: посылка заканчивается сбоем самого сервера, который ни во что не засчитывается, а в журнале преподавателя сказано проверить nvidia-smi внутри контейнера. Всплеск мимо ограничения может за секунды до второго замера отнять память у соседей по карте: посылку, которой не хватило видеопамяти (torch.OutOfMemoryError), пока исполнитель останавливал другую посылку на той же карте за выход за долю, один раз возвращают в очередь, с нашей строкой об этом, и эта попытка не засчитывается. Если посылкам не отдано ни одной карты, соревнование с «Видеокартой» сразу отказывает в загрузке и в проверке бейслайна и называет причину: никто не ждёт в очереди карту, которая не придёт.

Чего доля не даёт. Посылки на одной карте пользуются её вычислениями по очереди: модель, которая держит карту занятой, при трёх посылках на карте учится примерно втрое медленнее, чем одна, а предел времени тетради считает это время. Доля бережёт память, а не скорость: поднимите предел времени или посадите на карту меньше посылок. Небольшая модель между своими шагами оставляет карту свободной и соседей почти не замечает, см. замер ниже. В очереди GPU-посылке нужны свободный исполнитель и свободная доля карты; пока она ждёт карту, процессорные посылки за ней проходят вперёд.

Что карта даёт занятию. Замер 13 октября 2026 года на Vast VM с 61 vCPU, 98 ГБ памяти и 2 × RTX 4090 (по 24 ГБ): 25 участников в один момент отправили эталонное решение соревнования по распознаванию букв — небольшую свёрточную сеть; 2 ядра, 4 ГБ и 600 секунд на посылку; kaggle-gpu, — и каждая посылка получила оценку. Прогон — время, которое посылка исполнялась; вердикт считается от её загрузки.

Карта сокращает один прогон этой тетради в пять-шесть раз, и дальше занятие ждёт очередь, а не прогон: восемь посылок на карте шли почти так же быстро, как четыре, а две карты по восемь выдали вердикт всем 25 примерно за минуту. Тяжёлой модели лишние посылки на карте помогают меньше, и ей ещё нужно уместиться в долю поменьше. При смешанной нагрузке — 10 GPU-посылок и 4 процессорных на той же машине — очередь держала своё правило: процессорные посылки не ждали за GPU-посылками.

На Kubernetes долю определяет кластер: значение чарта gpu.competitions.resource называет ресурс device plugin, который просит GPU-посылка, — целую карту, реплику time-slicing или часть MIG; см. эксплуатацию. Сколько GPU-посылок одновременно уходит в кластер, задаёт gpu.competitions.slots, по одной, пока оно не задано: очередь держит там столько и пропускает процессорные посылки мимо остальных, как мимо занятой карты здесь. Сам Colloq там ничего не ограничивает и не проверяет: у части MIG своя память, а реплики time-slicing делят память карты без всякой границы между собой. И карта там не уходит из пула комнат: GPU-комнаты просят nvidia.com/gpu, поэтому с этим именем посылки берут единицы с карт комнат, и GPU-комната, которой не хватило свободной карты, не запустится, пока их держат посылки. Если на занятиях работают GPU-комнаты, дайте посылкам собственный ресурс, см. узлы с GPU.

Очередь и пульт

Очередь одна на весь инстанс: она лежит в базе и переживает перезапуск сервера. Сколько посылок исполняется одновременно, по умолчанию считается по машине («Авто»): её ядра и память за вычетом 2 ядер и 2 ГБ, оставленных занятию, делятся на ядра и память посылки по умолчанию. Своё число владелец задаёт во вкладке «Ресурсы» панели, см. ресурсы. Очередь честная по людям: вторая посылка одного человека встаёт за первыми посылками остальных, поэтому один участник не займёт исполнитель на всю пару.

Пульт соревнования (вкладка «Посылки») показывает, что исполняется сейчас, кто ждёт, пять чисел сводки и ленту посылок. В меню строки: открыть исполненную тетрадь, посмотреть весь вывод, исполнить заново, пересчитать метрику, не засчитывать. Полоса исполнителя в списке соревнований позволяет приостановить очередь, а у идущего прогона есть кнопка «Убить». Владелец удаляет соревнование пунктом «Удалить соревнование» в меню его строки в списке, и сначала уходят его прогоны: ждущие посылки покидают очередь, а идущие убиваются, и удаление ждёт их остановки, до 30 секунд на каждую. Если какая-то за это время не остановилась, ничего не удаляется, хотя ждавшие посылки остаются отменёнными, и удаление можно повторить через минуту.

Чтобы никто не подгонял решение под публичный лидерборд десятками посылок, поставьте дневную норму посылок. Норму тратят только посылки, получившие оценку. Упавшие — ошибка в тетради, лимит времени или памяти, непринятый ответ, сбой метрики или самого сервера — и отменённые её не тратят; посылка в очереди временно занимает место и возвращает его, если падает. От бесконечных падений защищает отдельный потолок упавших посылок: не больше 10 в день на участника или трёх норм, если это больше (сбои метрики в него не идут). Упёршийся в потолок участник видит свой отказ, отдельный от нормы. Без нормы (0) нет и потолка.

Участники и ключ входа

Участник соревнования — не житель комнаты: его личность принадлежит всему инстансу. Вступая, человек указывает логин Telegram или почту — под этим именем он стоит в лидерборде — и получает ключ входа вида K7Q-M2X-9FD и ссылку к нему. Тем же ключом он возвращается к своим посылкам с другого устройства, из другого браузера или после очистки данных. Логин или почта — это один человек: под именем, которое в соревновании уже есть, вступить нельзя. Отказ предлагает войти по своему ключу, и второй личности с другим ключом не появляется.

Ключ лежит в карточке «ВАШ КЛЮЧ ВХОДА» на странице соревнований — её видно каждый раз, а не однажды. В базе самого ключа нет: хранятся его отпечаток и копия, зашифрованная секретом инстанса, поэтому украденная база без секрета не открывает ни одного входа.

Если участник ключ потерял, выдайте новый на вкладке «Участники». Старый перестаёт действовать в ту же секунду — вместе со всеми вкладками, которые были на нём открыты.

Дедлайн и разбор

Когда дедлайн проходит, приём посылок закрывается сам, а итоговый лидерборд открывается — если в настройках выбрано «открыть сам после дедлайна». Второй вариант — «Открою вручную — на разборе»: тогда итоги показывает кнопка, и вы решаете, в какую минуту пары их увидят.

«Завершить сейчас» закрывает приём раньше срока. После дедлайна нажимать её не нужно: соревнование и так считается завершённым — в списке у участников и в панели оно стоит среди завершённых, а в шапке пульта вместо «Завершить сейчас» появляются «Закрыть поздний приём» или «Принимать поздние» и, если итоги открываются вручную, «Открыть приватный лидерборд».

Тем, кто доделывает решение после звонка, поможет переключатель «Поздние посылки» в разделе «Сроки и зачёт». С ним после дедлайна и после «Завершить сейчас» посылки принимаются дальше: исполняются, получают публичный счёт и тратят дневной лимит по тем же правилам, что и обычные. Но в зачёт поздняя посылка не идёт никогда: её нет в местах, лидербордах, сводке и ожидании итогов, выбрать её для зачёта нельзя. Итоговый счёт участник увидит, когда откроются итоги. У него на странице она отмечена «после дедлайна · вне зачёта», а на пульте у неё отметка «ПОЗДНЯЯ» и свой фильтр «Поздние». Поздней становится посылка, загрузка которой началась после дедлайна; начатая вовремя и докачанная в пределах двух минут остаётся в зачёте. Ждущую проверки посылку, отправленную вовремя, поздняя не заменяет. Пока приём поздних открыт, это видно в списках: у участников соревнование стоит среди завершённых с отметкой «приём поздних посылок открыт» и кнопкой, а в панели под «ЗАВЕРШЕНО» написано «поздние принимаются» и сколько их пришло.

Если на идущем соревновании перенести дедлайн позже, посылки, отправленные до нового дедлайна, становятся обычными: попадают в лидерборд и в зачёт. Перенос раньше никого поздним не делает. После «Завершить сейчас» перенос ничего не меняет: итоги закрыты вручную.

На разборе пригодится «Лидерборд на проектор» — отдельное окно с одной таблицей, без имён файлов и служебных отметок.

Дополнительные пакеты

Во вкладке «Пакеты» участник видит закреплённую версию Python и полный состав базы. Дополнительные библиотеки можно указать по одной на строку или загрузить из requirements.txt. Комментарии — отдельной строкой или после запроса (numpy==1.26 # для метрики) — и пустые строки не входят в лимит 32 запросов; весь файл ограничен 8 КиБ. Сервер заранее проверяет совместимость, скачивает готовые wheels из PyPI и проверяет установку без сети. Версии базовых пакетов менять нельзя.

Готовый набор выбирается перед явным подтверждением отправки тетради. Он и базовый образ закрепляются за посылкой; изменение выбора не меняет повтор старой посылки. Набор ставится в память посылки при каждом запуске и считается в её лимит: ему можно не больше половины, остальное — ядру, данным и рабочей папке. Набор больше этого не выбрать, и участник видит, сколько он займёт. На Docker-пути для подготовки требуется Docker Engine 28 или новее. Во время исполнения тетради и метрики интернет выключен.

Проверки и повторное исполнение

Каждая попытка получает отдельные каталоги и идентификатор. Пересчёт активной посылки ждёт окончания текущей попытки; старый CSV не может стать результатом неудачного нового запуска. Изменение метрики, данных, базового окружения или стартовой тетради требует актуальной проверки бейслайна. После изменения данных или окружения одного пересчёта метрики недостаточно: тетрадь нужно исполнить снова.

Доступность исполнителя

Посылки и подготовка пакетов исполняются там же, где ядра комнат: на Docker-пути (готовый образ сервера, colloq start) — в одноразовых контейнерах того же Docker, на k3s — в подах, которые запускает брокер. Если исполнитель или подготовка пакетов недоступны, интерфейс называет причину и не принимает работу в очередь; /api/health сообщает о каждой возможности отдельно. Соревнованию с «Видеокартой» нужна ещё и доля карты: если посылкам не отдано ни одной карты (на Kubernetes — не задан GPU-ресурс для посылок), оно отказывает в загрузке и в проверке бейслайна с этой причиной.
